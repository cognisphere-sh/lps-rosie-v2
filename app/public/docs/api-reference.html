API reference

The LPS app's screens get and save their data through a set of web addresses on the app's own server, called the API. This page lists every one of them: who may call it, what it expects, what it returns and what else it changes.

EngineersReference~45 min read

In short

If you are not an engineer, this section is enough:

  • The API is the back office of the app. Every button in the LPS app (saving a price, sending an availability request, confirming an order, chatting with Rosie) calls one of these addresses. The browser never talks to the database or the AI agents directly. It always goes through this API.
  • Three kinds of caller. Admins (the LPS team) can call almost everything. Partners (supplier companies with a portal login) can call only the partner portal API, and only for their own company. Anyone holding a public link can open, and for availability requests answer, that one shared request or order, plus any agent report page marked public.
  • Sign-in is a cookie. After signing in, the browser holds a signed cookie that is valid for 14 days. Every call is checked against it before it reaches any data.
  • Some saves wake Rosie. When a supplier submits an availability request, or confirms or updates an order, the API sends a short message to the AI agent Rosie so she can follow up. Ordinary saves do not wake her.
  • Nothing important is deleted quietly. Availability requests are never deleted on their own, only together with their whole job. Most catalogue deletes are "soft" (the record is hidden, not erased). Deleting a whole job, or a job line, is permanent, and is described as such below.

Conventions

These rules apply to every route unless the endpoint says otherwise.

Base URL and transport

  • Same origin. All routes live on the app's own host (the production domain behind nginx, or http://localhost:3000 in development). There is no separate API host, no versioned prefix and no CORS configuration: the API is meant to be called by the app's own pages.
  • JSON in, JSON out. Request bodies are JSON (content-type: application/json) except chat file uploads, which send the raw file. Responses are JSON except redirects, file streams, server-sent event (SSE) streams and artifact HTML.
  • Route handlers. Each endpoint is a Next.js 16 App Router route.ts file. There are 53 of them, exporting 74 method handlers, plus one server-rendered page (the private artifact viewer) and one rewrite (the Google sign-in callback).
  • Unexported methods. Calling a method a file does not export (for example DELETE /api/availability-requests/:id) gets Next.js's own 405 Method Not Allowed.
  • Path ids. Most routes parse numeric path ids with Number.parseInt(raw, 10), which is lenient (12abc reads as 12). The order routes and a few others use Number() plus a "positive safe integer" check, which is strict. Each endpoint notes which.

Cookie authentication

The app runs its own sign-in. POST /api/auth/login checks the password against Supabase Auth and then sets the app's own session cookie:

A session fails closed: a bad shape, a bad signature, an expired token, a missing secret, an unknown role, or a role/supplier mismatch (a partner without a supplier id, or an admin with one) all read as "signed out".

The request gate

Every request passes through app/proxy.ts (Next 16's replacement for middleware) before it reaches a route. It runs on every path except Next.js internals and any path whose last segment has a file extension (so static files such as /manifest.json, /sw.js and this handbook are never gated). It decides, in this order:

  1. Ungated paths pass. /login and /api/auth/*; public artifact pages /a/<agent>/public/artifacts/<slug>; and public link pages and APIs matching /(api/)?public/(availability|orders)/<uuid>, for every HTTP method.
  2. No valid session. API paths get 401 {"error":"unauthorized"}. Pages redirect to /login?next=….
  3. Password change pending. When the session's must-change-password flag is set, API paths get 403 {"error":"password change required"} and pages redirect to /change-password. (/api/auth/* already passed in step 1, so the change-password form and sign-out keep working.)
  4. Partner outside the portal. A partner session on any path not under /partner or /api/partner (and not /change-password) gets 403 {"error":"forbidden"} for APIs, or a redirect to /partner/<supplierId> for pages.
  5. Otherwise the request passes. An admin reaches everything.

How routes reach data

  • Server-side only. Every route uses the server-only Supabase client in app/lib/supabase.ts (env vars SUPABASE_URL, SUPABASE_SECRET_KEY). That key bypasses row-level security, so authorisation lives entirely in the gate, the handlers and the database functions' own guards.
  • Business rules in the database. Many writes call Postgres functions (RPCs) such as create_order or answer_availability_request, and triggers enforce lifecycles (for example "an availability request can never be deleted"). The RPC's error message becomes the API's error message.
  • Change history. Writes to jobs and to a line's own fields (name, size, demand, internal note) are recorded in job_request_changelog by a trigger. A line's status, price, availability and customer note live on its selected candidate, which has no changelog, so edits to them are not recorded there. App writes are attributed to the database role, because the app does not set an actor.
  • Live updates are a side effect of every write. The eight tables job_requests, job_request_items, availability_requests, candidates, orders, order_items, customers and suppliers (JOB_REALTIME_TABLES) are watched by Supabase Realtime. Any change to them makes the app send a data-free {"type":"jobs"} signal on /api/chat/events and /api/partner/:id/events, and open screens reload. This is not repeated under each endpoint.

Notifications to Rosie (supplier events)

A handful of routes tell Rosie that a supplier did something. They call notifySupplierEvent (app/lib/notify-supplier-events.ts), which POSTs to the harness's supplier-events plugin at ${HARNESS_URL}/webhook/rosie/supplier-events/notify with header x-app-secret (env SUPPLIER_EVENTS_APP_SECRET) and a 5-second timeout.

  • Best effort. If the secret is not set, nothing is sent. A failure is logged and never fails the API call.
  • Event types: availability_updated, availability_submitted, order_updated, order_status_saved and order_status_updated (defined but sent by no route).
  • Only some events wake Rosie. The plugin accepts availability_updated but deliberately does not deliver it ({"ok":true,"delivered":false}). Submissions and order events are delivered onto the Rosie thread of the AR's or order's job, jr-<job id> (sent as threadId; main when there is no job), because that thread owns all of the job's supplier work. See Harness plugins.

Jobs and job lines

Jobs (stored as job_requests, shown as JR-<id>) are a customer's quote; their lines are job_request_items; each line can have supplier candidates (candidates). Every line has a default candidate (the APS original, created with the line) and a selected one; a line's status, price, available quantity and customer note are read from its selected candidate (view job_lines, since migration 0130), while the line itself keeps only the customer's ask (name, size, quantity, internal note). Rosie writes most job content from chat; these routes read jobs and handle the structural edits. Field-level edits to jobs and lines go through PATCH /api/rows. See Jobs and job lines.

DELETE /api/requests/:id

Audience: Admin (gate). Source: app/app/api/requests/[id]/route.ts; RPC delete_job_request; trigger close_orphaned_availability_on_job_delete

Permanent

This deletes the job with everything of it: its lines and all their candidates, its availability requests, its orders and its change history. It cannot be undone.

The RPC deletes the job_requests row (active or not). In the same transaction the trigger close_orphaned_availability_on_job_delete (migrations 0139, 0141, 0146):

  • deletes the job's orders (every order belongs to exactly one job) and, with them, their lines;
  • deletes the job's lines, which takes all their candidates, asked ones included;
  • deletes the job's availability requests. This is the only way an AR is ever deleted: the guard that otherwise refuses AR deletes lets this one trigger through;
  • writes a deleted_job_threads marker for Rosie's jr-<id> thread, which queues chat cleanup in the harness and blocks late chat writes.

Changelog rows cascade by foreign key.

Response: 200 { ok: true, deleted: { items, changelog, availabilityRequests, availabilityRequestItems, orders, orderItems, threads, answers } }. availabilityRequests and availabilityRequestItems are the real counts of deleted ARs and their candidates; only answers is always 0. Errors: 400 bad id; 404 not found; 500.

POST /api/requests/:id/chat-parties

Audience: Admin (gate). Source: app/app/api/requests/[id]/chat-parties/route.ts, jobChatParties in app/lib/job-chat.ts

Availability requests

An availability request (AR, shown as AR-<id>) asks one supplier what they have for one job's lines. The AR's lines are candidates rows linked to it. Admins use these routes; suppliers answer through the partner portal or a public link. See Availability requests and Status lifecycles.

Rules the database enforces

An AR is never deleted on its own, only together with its job; moving it to Draft hides it from the supplier. There is one AR per job and supplier; asking again adds lines to the existing one. A non-draft, non-closed status needs an active, open job. Draft cannot jump straight to Processing or Completed. Draft and Closed clear the public link. Nothing returns an AR to New automatically (since migration 0130): reopening is explicit (reopen_availability_request), candidates can be added only to a Draft or New AR, and no LPS edit to the header or the answers changes the AR's status.

Orders

A supplier order is created once the customer confirms. Each order belongs to one job and one supplier (migration 0146), and there is at most one open order per job and supplier: more lines go onto it. LPS ticks job lines, and each order row is a copy of that line's selected candidate (one row per candidate). Pickup or delivery and the target date are the job's; the order carries additional details for the supplier (an ordered list of fields), a change log and the supplier's reply. All admin order routes check the admin role in the handler as well as at the gate (401 unauthorized with no session, 403 forbidden for a non-admin). See Supplier orders.

Artifacts

Agents can publish HTML report pages ("artifacts"). Each has a public/private switch: private pages are for admins, public ones for anyone. Pages are served under a sandbox content-security policy without same-origin rights, so agent HTML cannot touch the app's session. See Harness plugins.

Shared rules (app/lib/artifacts.ts): :agent must be in the ARTIFACTS_AGENTS list and :slug must match ^[a-z0-9][a-z0-9-]{0,63}$, else plain-text 404 not found before any upstream call. Upstream is ${HARNESS_URL}/webhook/<agent>/artifacts/<public|private>/<slug>. HTML responses keep only content-type, content-security-policy, referrer-policy, x-content-type-options and cache-control. "Signed in" here means a valid app_sid with the admin role, verified locally.

GET /a/:agent/public/artifacts/:slug

Audience: Public. Source: app/app/a/[agent]/public/artifacts/[slug]/route.ts

Fetches the page from the plugin without credentials. The plugin serves it only while the artifact is public, and answers 404 otherwise. Errors: 404; a harness network failure gives a bare 500.

GET /a/:agent/private/artifacts/:slug (page)

Audience: Admin (gate). Source: app/app/a/[agent]/private/artifacts/[slug]/page.tsx, ShareToggle.tsx

A server-rendered page, not a route handler. It reads the artifact's metadata ({ slug, visibility, url, privateUrl, bytes, modified }) from the plugin with x-artifacts-secret, then shows a Public/Private toggle, a "Link to share" field and an iframe of the raw route below. Unknown artifact → the app's own not-found page ("Nothing growing at this address", app/app/not-found.tsx). Signed-out visitors go to /login; partners are redirected to their portal.

GET /a/:agent/private/artifacts/:slug/raw

Audience: Admin (gate + handler). Source: app/app/a/[agent]/private/artifacts/[slug]/raw/route.ts

The private page's HTML, fetched with x-artifacts-secret and no caching. Errors: plain-text 401 sign in (checked first); 404; otherwise the plugin's status.

POST /a/:agent/private/artifacts/:slug/share

Audience: Admin (gate + handler). Source: app/app/a/[agent]/private/artifacts/[slug]/share/route.ts

Body: { public: boolean }. Anything but literal true (including a bad body) is sent as false, making the page private.

Response: the plugin's answer (the updated artifact info) with content-type: application/json and cache-control: no-store. Errors: 401 sign in; 404. Side effects: flips the artifact's visibility, which decides whether the public link works.

Quirks worth knowing

Behaviour that is correct as built but easy to trip over when calling the API directly.

  • Status codes vary by route for similar failures. AR edits answer 409 for any error mentioning "closed" and 400 for everything else, including "not found". Candidate actions return business-rule refusals as 500. POST /api/requests/:id/items returns "not found" as 400. A non-numeric supplier range filter returns 500. PATCH /api/rows returns 200 for an id that matches no row (job line values aside).
  • Lenient id parsing. Routes using parseInt accept 12abc as 12; order routes, public links and /api/customers/:id/chat are strict.
  • Same value, different labels. need_to_order is "Can Order" on job lines but "Need to Order" on order lines; AR answers use a separate value, can_order. An AR in submitted is labelled "Completed".
  • supplierNote writes note_for_supplier. The AR-wide note is a shared-audience column; on supplier submit the supplier is its author. Sending null clears it.
  • Portal data-change signals are global. /api/partner/:id/events fires for any watched change, not just the supplier's; it carries no data.
  • Admin-only by gate alone. Every internal route labelled "Admin (gate)" above, including /api/chat/threads, /api/chat/events, /api/chat-directory, /api/rows and the private artifact page, relies entirely on the proxy for its admin restriction. Only the order routes, the portal-login routes, the chat and harness proxies and the private artifact raw/share routes re-check the role themselves.
  • No login throttling is implemented on POST /api/auth/login.
