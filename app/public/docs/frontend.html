Frontend: routes and components

The LPS app is one website with two audiences. The internal team gets the full workspace with suppliers, plants, photos, customers, jobs and the AI agents, and suppliers who are LPS Partners get their own small portal. This page lists every screen, who can open it, how it gets its data and how it looks on a phone compared with a desktop.

TechnicalDevelopersBusiness: first section~25 min read

In short

  • One web app, two audiences. The internal team (the admin role) gets the whole workspace: Suppliers, Plant search, Photos, Customers, Jobs, Settings, and chat with the AI agents Daisy, Rosie and Nova. Suppliers who are LPS Partners (the partner role) sign in to the same site, but they only see their own supplier portal under /partner/<id>. There they answer availability requests, see their orders and chat with Local Plant Supply.
  • A few pages need no sign-in. These are the login page, a shared availability-request link, a shared order link, an agent artifact that has been made public, and any static file, such as the files that let you install the app on a phone. This handbook is the exception: it needs an admin sign-in.
  • Pages draw first, then fetch. Every screen runs in the browser and asks the app's own /api/… endpoints for data. No page reads the database while it is being built on the server.
  • Job and portal screens refresh themselves. When an agent, a supplier or a colleague changes something, the server sends a short "something changed" signal and open job, customer-detail, availability-request and supplier-portal screens reload what they show. If the live connection drops, a slow background check takes over. The Suppliers, Plant search, Photos and Customers lists reload when you search or page. Suppliers and Plant search also reload when you pull to refresh on a phone.
  • Phone and desktop get different layouts of the same app. The switch happens at 900 px wide. A desktop has a left menu rail, a chat panel docked on the right and spreadsheet-style tables. A phone has a bottom tab bar, cards instead of tables, full-screen chat, pull-to-refresh and a "More" (⋯) menu.
  • It installs like an app. On phones and desktops the app can be installed as a Progressive Web App (PWA) that opens full screen on Suppliers. iPhone users get "Add to Home Screen" instructions instead of an install button.
  • Settings holds the AI model connection, the app's accent colour and one tab per agent with its model, Google account, scheduled tasks, chat colour and wallpaper. Colours and wallpapers are saved on each device. Everything else is saved on the agent server (the harness).
  • Look and feel comes from the "Local Plant Supply UI" design system (lps-ui, built on shadcn/ui). It has an Edge Teal accent, the Inter and Playfair Display typefaces, light and dark modes, and a fixed set of status colours ("tones") for job, line and request states.
Where to stop

If you only need to know what the screens are and who uses them, the summary above and the route map are enough. The rest of the page is for people changing the app.

Who can open what

One gate decides who reaches which URL: app/proxy.ts. Next.js 16 calls this file proxy; older versions called it middleware. It runs before every request it matches.

Supplier partnerpartnerOnly /partner/<their supplier id>/… and /change-password./partner/<supplierId>

How the gate decides

  1. Skip static files. The matcher is /((?!_next/static|_next/image|favicon.ico|.*\.[^/]+$).*). Any path that ends in a file extension never reaches the gate. That covers /manifest.json, /sw.js, icons and agent avatars. A second matcher entry, /docs/:path*, pulls this handbook back into the gate, so it needs an admin session. Its /docs/onboarding/ videos pass as PUBLIC_DOCS, because the public /partner-onboarding page plays them.
  2. Let public paths through. PUBLIC_PREFIXES = ['/login', '/api/auth']. The regex PUBLIC_AVAILABILITY matches /public/availability/<uuid>, /public/orders/<uuid> and their /api/public/… twins (36-character UUID token). PUBLIC_ARTIFACT matches /a/<agent>/public/artifacts/<slug>.
  3. Require a session. resolveUser(cookie) (lib/session.ts) reads the signed app_sid cookie. With no session, /api/* answers 401 {"error":"unauthorized"} and pages redirect to /login?next=…. The next value comes from jobLoginReturn().
  4. Force a password change. If mustChangePassword is set, everything except /change-password is refused: the API answers 403 {"error":"password change required"} and pages redirect to /change-password.
  5. Fence partners in. A partner outside PARTNER_PREFIXES = ['/partner', '/api/partner'] gets 403 {"error":"forbidden"} from the API, or a redirect to /partner/<supplierId>. Which company a partner may open is checked per route by canAccessSupplier() in lib/auth.ts, not by the gate.
Keep static files ungated

The PWA depends on the file-extension rule in the matcher. If it is tightened, the install files start redirecting to /login. Anything placed in app/public/ is public, except under /docs/.

next.config.ts adds one permanent redirect, /portal/:path* → /partner/:path*, for old supplier links from before the portal was renamed on 2026-08-26. It also adds one rewrite, /api/gws/oauth/callback → ${HARNESS_URL}/api/gws/oauth/callback, for the Google OAuth browser redirect. Every other call to the harness goes through the allowlisted pass-through app/api/harness/[...path]. The sign-in flow itself is covered in Auth, roles and security.

App shell, frame and layout

There are two layout.tsx files. The root layout draws no navigation. The (workspace) route group's layout mounts one persistent WorkspaceShell around every admin page, so moving between Suppliers, Jobs, Settings and the rest swaps only the page: the rail, the agent chat (its thread, scroll position, draft and live connection) and the bell stay mounted. The full/peek chat size, the Account and ⋯ menus and the mobile Agents view still reset on a page move, and the AR drawer is keyed by route, so an open drawer closes. Supplier portal pages are outside that group and each mounts its own PartnerFrame. Both chromes are built on one shared layout, WorkspaceFrame. Preferences that must outlive a reload (rail open, chat width, theme) are kept in browser storage.

Root layout (app/app/layout.tsx)

  • Fonts via next/font/google: Inter → --font-inter, Roboto → --font-roboto, Playfair Display → --font-playfair. globals.css maps them to --font-sans, --font-chat and --font-serif. Because the fonts are fetched from Google at build time, next build needs network access.
  • Metadata: title "Local Plant Supply", manifest: '/manifest.json', icon /lps-cactus-icon-192.png, Apple touch icon /lps-cactus-apple-touch-icon.png, and appleWebApp: { capable: true, statusBarStyle: 'black-translucent', title: 'Plant Supply' }.
  • Viewport: fixed charcoal themeColor: '#1A1A1A', independent of saved accent and light/dark mode, and viewportFit: 'cover', which gives the env(safe-area-inset-*) paddings a value in full-screen mode.
  • Body: min-h-dvh bg-background text-foreground font-sans antialiased, wrapped in <PWAProvider>, with <PWAInstallPopup /> and <RouteTransitions /> after the children.

Next to it sit app/app/not-found.tsx and app/app/error.tsx, which replace Next's stock 404 and error screens (see Page not found and load errors).

Route transitions

Every page move in the workspace and the supplier portal is animated with the browser's View Transitions API, so it shows where the new view came from. RouteTransitions (components/workspace/route-transitions.tsx) catches in-app link clicks inside the frame and hands them to lib/view-transitions.ts. A link's own click handler still wins: if it prevents the default (an unsaved-changes confirm, the tab bar closing an overlay), the transition steps aside.

  • Kinds (TransitionKind): lateral (another rail destination; the page column slides along the rail), deeper (a list row opens its record; the record unfolds out of the pressed row and the row's name or JR reference flies into the title), back (the record folds back into its row) and swap (same level, such as another job or tab; a short slide). Links can steer a move with data-vt-kind and data-vt-subject, or opt out with data-vt="off".
  • "You are here" marks carry a permanent view-transition-name so they glide on every move: lps-here on the rail, lps-here-tab on the mobile tab bar and lps-history-tab on the portal history tabs. Tab panels slide toward the tab chosen (switchTab).
  • Timing: moves run at most 300 ms. Under reduced motion every move is a 120 ms crossfade with nothing travelling. Browsers without the API, and background tabs, simply navigate.
  • The ::view-transition-* CSS is injected at runtime by lib/view-transitions.ts, because Turbopack's CSS pipeline drops those rules from globals.css.

Page by page

The business meaning of each screen is covered on the domain pages (Jobs, Availability requests, Supplier orders, Catalogue). This section records what the UI does.

Sign in and change password

  • AuthFrame (components/auth-frame.tsx) is shared by both pages: an Edge Teal brand field with the leaf mark, the Playfair "Local Plant Supply" wordmark (the page's h1) and an animated SproutRow of seedlings, beside a borderless form card. On a phone the brand field shrinks to a band above the form.
  • /login: the form card is headed "Sign in", with the line "Sign in to browse suppliers and availability, or to answer availability requests as an LPS Partner." It has Username and Password fields (named username and password with autoComplete hints for password managers; the username field has autoCapitalize="none" and autoCorrect="off") and a "Sign in" button ("Signing in…" while busy). A 401 shows "Invalid username or password.". Other failures show the server's error or "Could not sign you in. Try again in a moment.". A network failure shows "Could not reach the server.". On success the page calls router.push(loginDestination(next, body.next ?? '/')). The page sits inside Suspense because it uses useSearchParams.
  • lib/login-return.ts: jobLoginReturn keeps only /jobs?jr=<positive integer> and otherwise returns just the pathname. loginDestination rejects //, control characters, encoded slashes, hashes and /login or /api paths, and it never overrides /change-password. This prevents open-redirect tricks through ?next=.
  • /change-password: the same AuthFrame, with the form card headed "Choose a password". It uses ChangePasswordForm (Current password, New password, Confirm new password) with a minimum of MIN_PASSWORD_LENGTH = 10, the error "The two do not match." and the button "Save and continue", then goes on to next.

Suppliers list (/suppliers)

  • There is one row per company. Companies with more than one location get an expander ("n of m farms").
  • Filters: search ("Search name, contact, email, city…"), a quick Type multiselect, and Advanced filters (a 480 px popover on desktop, a bottom sheet on mobile) with "Name contains", City and an LPS Partner toggle. Server-side filter keys (SUPPLIER_FILTERS) are category, city, state, lps_partner, availability_source_type, availability_update_days, name, notes.
  • Data: debounced (300 ms) GET /api/suppliers. Facets come from ?facets=1&q=. A second request, ?counts=1&ids=, fills the item count per location. Edits use PATCH /api/rows.
  • Desktop: a fixed-layout table with sticky headers (ColumnHead: sort, resize, drag to reorder) and a sticky actions column. That column holds the Rosie and Daisy chat buttons (company rows only) and "Hide company/farm until refresh", which you can undo from a "n rows hidden · Restore" footer. Default columns: name, category, state, inventory_sources, item_count, website, primary_contact_name. There is a pager.
  • Mobile: cards showing the name, partner tag, city/state, item count, category badge, primary contact, "Last ingested …" and an "Open company →" link ("Open supplier →" for a single-location supplier). Paging is "Load 50 more" (or "Retry load 50 more" after a failure).
  • The summary reads "<visible>/<total> Companies". Loading shows SearchOverlay with rotating captions.

Supplier profile (/suppliers/[id])

  • Tabs (?tab= deep link, default inventory): Inventory, Contacts, Farms (only for multi-location companies), Availability requests, Notes, Files, Portal access. ?tab=requests&ar=<id> opens one request.
  • Explicit edit mode: profile fields stay read-only until you press Edit supplier, which becomes Save / Cancel. A beforeunload guard and "Discard your unsaved supplier changes?" protect unsaved edits. "LPS Partner" is read-only because it is derived from portal logins.

Data loading patterns

No server components read Supabase

A common assumption is that pages are server components that query Supabase. In this app they do not. No page or component imports @/lib/supabase. Every page is a client component (or a thin server wrapper around one) that fetches the app's own /api/* routes from the browser. Only the API route handlers (and the server-only lib/* modules they call) talk to Supabase, through the server-only client in lib/supabase.ts, which is built from the server environment variables SUPABASE_URL and SUPABASE_SECRET_KEY (names only; the key never reaches the browser). The only server-side fetch in a page is the private artifact page calling the harness.

  1. Draw the frame. An admin page renders Shell inside the already-mounted workspace layout; a portal page mounts PartnerFrame. The page shows a loader or skeleton.
  2. Fetch from /api. The browser calls the app's routes with the app_sid cookie. The route checks the role and queries Supabase server side. See API reference and Architecture.
  3. Render and keep fresh. The page renders the JSON and subscribes to live invalidations (next section).
  4. Write back through /api. Edits go to whitelisted write routes, then the page re-reads or patches its local state.

Live updates

Screens stay current without anyone pressing refresh. The server holds one Supabase Realtime subscription and relays a tiny "jobs changed" invalidation to browsers over Server-Sent Events (SSE). The browser then re-reads its data from /api. Records and tokens are never pushed. The full pipeline is on Chat and live updates.

  • useJobUpdates(refresh, enabled, eventsUrl = '/api/chat/events') (lib/use-job-updates.ts) subscribes through subscribeEvents, which keeps one shared, reference-counted EventSource per URL. It calls refresh on isJobEvent events, on reconnect, on window focus, on online, on visibilitychange and on a 60 s fallback poll. Calls are batched with a 200 ms timer. If something changes while a read is running, it reads again. Nothing runs while the tab is hidden.
  • usePartnerUpdates(supplierId, refresh) is the same hook pointed at /api/partner/<id>/events.

Service worker (public/sw.js)

  • Cache name lps-app-shell-v1, fallback page /suppliers.
  • install calls skipWaiting(). activate deletes every other cache and calls clients.claim().
  • fetch handles only GET requests with mode === 'navigate' (whole-page loads). It goes to the network first and caches a copy when response.ok && !response.redirected. Offline, it serves the cached page (ignoreVary: true, because Next varies HTML on its router headers), then the cached /suppliers shell, then Response.error().
  • Nothing is precached, because an install-time fetch would only cache a redirect to /login. API calls and assets are never cached: stale supplier data would be worse than none.

Testing the UI

UI behaviour is tested with fast, in-process component tests. Visual changes also get a screenshot review before they go live.

  • Runner: Node's built-in node:test with node:assert/strict, run through tsx: pnpm --dir app test (tsx --test lib/*.test.ts lib/*.test.tsx). There are 78 test files in app/lib/.
  • Component tests (*.test.tsx) build their own JSDOM for each test and use @testing-library/react and @testing-library/user-event. There is no browser runner and no snapshot testing.
  • Typecheck: pnpm --dir app typecheck (tsc --noEmit, strict mode). There is no lint script.
  • Standalone checks: node lib/table-config.check.mjs and node lib/size-std.check.mjs. These are plain assert scripts that pnpm test does not run.
  • Single file: pnpm --dir app exec tsx --test lib/<file>.test.tsx. On the production server, run only the relevant files, because the full suite needs more memory than the host has.

Visual release check

  1. Preview. The visual-ui-release-qa skill (v2.1.0) previews the committed primary checkout with the normal dev server on its own port, pnpm --dir app dev --hostname 127.0.0.1 --port 3100, so the live app is never touched.
