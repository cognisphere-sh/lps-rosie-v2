Harness plugins

The AI agents can't reach anything outside the harness by themselves. Every connection is a plugin: the app's chat panel, Telegram, Gmail, timers, published pages, agent-to-agent messages, and the "doorbell" that wakes Rosie when a supplier acts in the portal. This page lists every plugin, who has it, how it is configured, what it receives and sends, and what happens when it fails.

EngineersOperatorsReference~25 min read

In short

If you read only this section, these are the main points:

  • A plugin is a connection. Rosie, Daisy, Nova and Lily each run inside the Cognisphere harness and see the outside world only through plugins. Each plugin can be switched on or off per agent.
  • Three plugins are custom-built for LPS and live in this repository under harness/plugins/:
    • Web Chat (webchat) is the chat panel inside the LPS app, and it also carries the supplier portal's chat with Rosie. Every conversation has its own saved transcript. Suppliers see only the messages meant for them.
    • Supplier Events (supplier-events) is the doorbell the app rings to wake Rosie when a supplier submits availability answers or changes an order in the portal, on the thread of the job the request or order belongs to. Saving answers without pressing Submit does not wake her, which keeps costs down.
    • Google Workspace (gws) checks an agent's Gmail inbox on a timer and wakes the agent with a short preview of each new email. It is a hardened local copy of the standard harness Gmail plugin.
  • Five plugins come with the harness platform: an admin console channel, a scheduler for timed reminders, agent-to-agent messaging, Telegram, and "artifacts" for publishing web pages with a private or public link.
  • Who has what. Rosie has the most plugins, and she is the only agent with Supplier Events. Daisy has Gmail, Telegram, web chat and artifacts. Nova has Telegram, web chat and artifacts. Lily is reachable on Telegram only. All four have the admin, scheduler and messaging plugins.
  • A broken plugin doesn't stop an agent. The harness marks that one plugin as failed and the agent keeps running on its other plugins. App-to-agent notifications are best-effort: if the harness is down, the supplier's save still succeeds and only the "wake Rosie" ping is lost.
What "user-space" means

Built-in plugins ship inside the installed harness package and are not edited here. User-space plugins are source code in this repository (harness/plugins/<id>/). A user-space plugin with the same id as a built-in one replaces it. That is how the local gws copy takes over from the standard one.

How plugins work

This section is the shared contract that every plugin on this page follows. The per-plugin sections assume it.

Three kinds

KindPlugins hereHow it is enabledCan it be changed here?
Core (built-in)admin, scheduler, agent-messagingAlways on for every agentNo. Core plugins can't be forked.
Catalog (built-in)telegram, artifacts, gwsPer agent, by creating harness/agents/<agent>/plugins/<id>/Only by forking into harness/plugins/<id>/ (cognisphere plugin add <id>). The fork shadows the bundled plugin.
User-space (custom)webchat, supplier-events, plus the gws forkPer agent, the same wayYes. Source lives in harness/plugins/<id>/.

Shape of a plugin

A plugin is harness/plugins/<id>/index.ts, which default-exports a class with:

  • manifest: displayName, description, configSchema and secretsSchema. Both schemas are JSON Schema, validated with defaults filled in.
  • start(ctx) and stop().
  • Optionally handleHttpRequest(req, res), served at /webhook/<agent>/<id>/*. The plugin sees the path after its own prefix (for example /notify).

User-space plugins don't import harness types. All three local plugins duck-type the interface.

The ctx object a plugin receives at start carries:

  • agentId, agentDir, stateDir (agents/<a>/plugins/<id>/state/) and inboxDir (…/inbox/)
  • config, secrets and timezone
  • notify(name, payload), which wakes the agent
  • httpBaseUrl and log
  • resetThread(channelId, threadIdOverride?), which the harness refuses while a batch is in flight on that thread

Waking an agent: notify and metadata

ctx.notify(name, payload) puts an event in the agent's durable queue (sessions/.events.db) and wakes the agent, or steers a run that is already live. The payload needs at least { text, channelId }. Optional fields are metadata, threadIdOverride, isSilent, doNotSteer and priority.

The runner wraps each event in a <harness-metadata> block:

  • The harness always adds Timestamp, Plugin, Channel and ThreadId, plus IsSilent, Retry or Continuation when they apply. These keys are reserved, and a plugin that sends them has them silently dropped.
  • Plugin keys are PascalCased (webchatThreadId becomes WebchatThreadId). Null values are dropped, arrays are comma-joined and objects are JSON-stringified.
  • The event name is not shown to the agent. A plugin that emits several kinds of event therefore puts an EventType metadata key on each one.

Threads

Each agent's agent.json sets threadIdStrategy: single (one global thread), plugin (one per plugin) or plugin_channel (one per plugin and channel). Rosie and Daisy use plugin_channel. Nova and Lily use single. A notify that carries threadIdOverride bypasses the strategy, and that is how webchat and supplier-events put events on a named thread such as jr-12 (or, for webchat, supplier-<slug>). Telegram and gws do the same thing with routing rules.

Seeds: prompt fragments, CLIs and skills

A plugin can ship a seed/ tree. On every agent start it is copied recursively into the agent directory, overwriting what is there:

  • system_prompts/plugin-<id>.md, the plugin's instructions to the agent
  • scripts/<id>/…, the agent's CLIs (the executable bit is re-asserted)
  • skills/<id>/<slug>/, plugin-owned skills
Never edit the agent copies

Seeded files in harness/agents/<agent>/ are overwritten at the next start. Change the seed under harness/plugins/<id>/seed/ instead. The agent copies of plugin-gws.md, plugin-webchat.md and plugin-supplier-events.md match their seeds byte for byte.

Enabling, config and secrets

  • A plugin runs on an agent if harness/agents/<agent>/plugins/<id>/ exists. Core plugins run anyway. A plugin directory may only appear on disk once the plugin writes state, so the set of system_prompts/plugin-*.md files is the reliable list of what an agent has.
  • An optional config.json in that directory is validated against configSchema.
  • Secrets live in harness/.secrets/secrets.json under <agent>.<plugin-id>.<KEY>, must be declared in secretsSchema, and are all injected into the agent's environment. Key names must be unique across an agent's buckets, which is why web chat uses WEBCHAT_SUPABASE_URL rather than SUPABASE_URL. Hand edits need an agent restart. Edits made in the console reload without one.
  • Plugins are discovered at boot only. A new harness/plugins/<id>/ needs a harness restart. When a built-in and a user-space plugin share an id, the user-space one wins.

Calling plugins over HTTP

The harness listens on the server itself (port 3142 by default; the deploy scripts set it with HARNESS_PORT), and the webhook router does not authenticate by itself. Each plugin checks its own callers, and there are two patterns:

  • In-harness callers (agent CLIs) send X-Webhook-Secret: $COGNISPHERE_WEBHOOK_SECRET. The harness generates that secret at boot and every agent's environment inherits it.
  • The Next.js app can't see that boot secret, so each plugin endpoint it calls checks a shared secret of its own. supplier-events and the web chat's api/app-* endpoints take it as X-App-Secret, and artifacts takes it as x-artifacts-secret. scripts/app/secrets.sh writes the same value into the agent's secrets bucket and into app/.env.local. The web chat's browser endpoints are different: the app sends the harness's own app secret (Authorization: Bearer <HARNESS_APP_SECRET> plus X-App-User), which scripts/server.sh writes into app/.env.local.

The agent environment the CLIs rely on is PI_AGENT_ID, PI_THREAD_ID, PI_WEBHOOK_BASE (<server>/webhook/<agent>), COGNISPHERE_WEBHOOK_SECRET and HARNESS_BASE_URL. According to the harness changelog, the runner exports HARNESS_BASE_URL to every agent process. agent-msg/send falls back to http://127.0.0.1:3142 when it isn't set.

Failure model

A plugin failure doesn't stop the agent. It is recorded as a failed plugin entry, visible in GET /api/agents/<agent> under plugins[].error and in the console. A missing required secret fails that plugin, not the agent. A load failure logs failed to load plugin. A healthy start logs agent started with the list of runningPlugins.

Supplier Events (supplier-events)

Supplier Events lets the web app tell Rosie that a supplier did something she should react to. It has no timers, no polling and no state of its own. It is one HTTP endpoint that turns a small JSON event into a wake-up on the right conversation: the thread of the job the AR or order belongs to. Its model is one job, one thread. Manifest description: "Wakes the job's thread when a supplier submits answers or changes an order through a portal or public link."

What wakes Rosie, and what doesn't

What happenedWhereEventWakes Rosie?
Supplier presses Submit or Re-Submit on an availability requestPartner portalavailability_submittedYes
Supplier submits through a public availability linkPublic linkavailability_submittedYes
An admin sets an availability request's status to Completed (submitted)Admin AR draweravailability_submittedYes
Supplier confirms an order, marks it ready or completed, or changes their own note on itPartner portal, order pageorder_updatedYes, only if something actually changed
Supplier saves a batch of order-line statusesPartner portal, order pageorder_status_savedYes
Supplier saves an answer or maps a line to a catalogue plant without submittingPartner portal or public linkavailability_updatedNo. Acknowledged and dropped.
An admin saves the supplier note, a line answer or plant details on an AR, or switches customer-detail sharing on or offAdmin AR draweravailability_updatedNo. Acknowledged and dropped.
Draft availability request created or editedAdminNone, or availability_updatedNo. Drafts are invisible to suppliers. Creating or sending one sends no event. An admin edit to a draft's note or lines goes through the same route as any other AR and sends only the dropped availability_updated.
Why saves don't wake Rosie

Suppliers often save answers several times before they submit. Each wake-up costs an agent turn, so since 2026-09-29 the plugin acknowledges plain saves and delivers nothing. Rosie only reacts when the supplier says "I'm done" by submitting. The changelog estimated the saving at about 52 turns, or $7, a week.

The wake-up contract

This is the full interface between the app and the plugin. The plugin side is covered by app/lib/rosie-thread-events.test.ts, which imports the plugin class directly and also checks the seeded prompt. The app's call sites are covered with a stubbed notifier in tests such as app/lib/orders.test.ts and app/lib/ar-item-details.test.ts.

Request

  • POST /webhook/rosie/supplier-events/notify on the harness (default http://127.0.0.1:3142, overridable with HARNESS_URL). The plugin sees the path /notify.
  • Headers: content-type: application/json and x-app-secret: <SUPPLIER_EVENTS_APP_SECRET>.
  • Body: one JSON object. Every event carries type, supplierId, supplierName and threadId, where threadId is the AR's or order's job thread, jr-<job_request_id>, or null when there is no job.
typeExtra fields
availability_submitted, availability_updatedavailabilityRequestId (positive integer), jobRequestId (positive integer or null)
order_updatedorderId, orderChanges: [{ field, previous, value }], 1 or 2 entries. field is status or noteFromSupplier. previous and value are strings or null. A status value must be processing, order_ready or completed.
order_status_savedorderId, changes: [{ itemId, status, note }], at least one. itemId is a positive integer, status a non-blank string and note a string. The plugin sets no upper limit; the app caps a batch at 500.
order_status_updatedorderId, orderItemId (positive integer), status (non-blank). Accepted and delivered, but no app route sends it today.

What Rosie receives

The plugin calls ctx.notify(type, { text, channelId, threadIdOverride, metadata }).

  • Thread. thread = trim(threadId) || "main". Both channelId and threadIdOverride are set to it, so Rosie's plugin_channel strategy is bypassed and the event lands on the job's thread.
  • Text, by type. <Supplier> is the trimmed supplier name:
    • Availability: <Supplier> submitted their answers on availability request AR-<id> (job request JR-<jr>). The part in brackets appears only when jobRequestId is present.
    • order_updated: <Supplier> <action> order O-<id>. Changes: <field>: "<previous>" → "<value>"; …, where <action> is marked ready for a status change to order_ready, marked completed for completed, confirmed for processing, and updated otherwise. Values are JSON-quoted, so a cleared value shows as null.
    • order_status_saved: <Supplier> saved <n> order status change(s) on order O-<id>.
    • order_status_updated: <Supplier> saved <status> for line <orderItemId> on order O-<id>.
  • Metadata, in the <harness-metadata> block:
    KeyPresent onMeaning
    EventTypeAllThe event type, because the notify name is not shown to the agent
    SupplierId, SupplierNameAllThe supplier
    AvailabilityRequestIdAvailabilityThe AR that was submitted
    JobRequestIdAvailability, when not nullThe AR's own job (availability_requests.job_request_id). The prompt treats it as a legacy hint only.
    OrderIdOrder typesThe changed order
    OrderChangesorder_updatedHeader changes: field, previous value, saved value
    OrderStatusChangesorder_status_savedLine changes: itemId, status, note
    OrderItemId, OrderItemStatusorder_status_updatedOne saved line status
  • isSilent, priority and doNotSteer are not set, so every delivered event wakes Rosie, or steers her current turn on that thread.
  • It is not a chat message. The wake-up writes no thread_messages row, so it doesn't appear in the job's transcript, the supplier's conversation or the bell. Only Rosie's later replies do.

Guarantees, and what is not guaranteed

PropertyBehaviour
Ordering with the dataThe app sends the event only after the database write commits. The event carries ids only, so Rosie always reads current state.
DeliveryBest-effort, at most once. There is no retry queue. If the harness is down, times out (5 s) or answers non-2xx, the wake-up is lost, and the app logs notifySupplierEvent: … to its console. The supplier's action still succeeds. One edge case: the supplier, thread and job lookup that builds the event runs after the write. Only the order-header route wraps it in its own try/catch. On the other routes, a failed lookup returns an error response even though the write has already committed.
DuplicatesNo deduplication or idempotency key. Each accepted POST is exactly one wake-up. A submit followed by a re-submit gives two wake-ups, and a test asserts this.
Latency costEvery caller awaits the notification, so a slow harness can add up to 5 s to the supplier's request.
Not configuredIf SUPPLIER_EVENTS_APP_SECRET is unset in the app's environment, notifySupplierEvent returns without sending anything.
OriginThe event has no "who did it" field. An admin marking an AR as submitted reads the same as a supplier submitting.

Rosie's side of the contract

The seeded prompt fragment (plugin-supplier-events.md) tells Rosie:

  • Always re-read the current AR or order before acting. Ignore events about deleted or closed records; a late event never reopens or edits them.
  • If newer saved edits followed a submission, relay only what was submitted.
  • Events land on the AR's or order's job thread (jr-<id>), which owns all of that job's supplier work. One without a job lands on main, which hands it to the owning job thread with the message-routing skill. The prompt calls this routing, not a message to the owner or a job.
  • availability_submitted: relay the answers to the AR's job (supplier-coordination skill, responses). The database has already copied the answers of selected candidates onto their job lines, and has moved a line whose selected asked row offers a substitute onto that substitute. Rosie alerts the owner and reports answers on other candidates.
  • order_updated: re-read the order, acknowledge it in the supplier's conversation, and update the job. order_status_saved and order_status_updated: re-read the order and lines, then follow up in the supplier's conversation. Each line note is saved as that row's note_from_supplier.
  • An AR belongs to one job (availability_requests.job_request_id), and so does an order (orders.job_request_id, migration 0146). JobRequestId is only a hint.
  • Never set selected_candidate_id from an event; only the owner picks a non-default candidate (the database alone moves a line to a supplier's substitute on submission). An event is not the owner's approval to contact anyone, is not customer acceptance, and doesn't change pickup or delivery. An AR submission doesn't confirm an order. Orders go New → Processing → Order Ready → Completed while their jobs stay Committed.

Thread routing: one job, one thread

The app names the job thread when it sends the event: jr-<job_request_id> from the AR's availability_requests.job_request_id, or from the order's orders.job_request_id (one job per order since migration 0146). That job thread owns all of the job's supplier work, so a supplier's submission or order change reaches the same conversation where Rosie handles that job. An AR without a job sends threadId: null, and the event lands on Rosie's main thread, which hands it to the owning job thread with her message-routing skill. The supplier's portal chat is a separate, shared supplier-<slug> conversation; Rosie routes each portal message from it to the job it concerns (see Web Chat).

Where the app sends events

The app helper is notifySupplierEvent(event) in app/lib/notify-supplier-events.ts. Two context builders fill in the supplier fields:

  • supplierAvailabilityEventContext(arId, forSupplierId?) in app/lib/availability-queries.ts reads the AR's supplier, the supplier's name and the AR's job_request_id, and sets threadId to jr-<job_request_id>, or null when the AR has no job. It works on closed history too.
  • supplierOrderEventContext(orderId, forSupplierId?) in app/lib/order-queries.ts does the same for an order, using orders.job_request_id, which is never null.

Config, secrets and lifecycle

  • Manifest: display name "Supplier Events". Enabled on Rosie only, and the app hard-codes rosie as the target.
  • Config: none. configSchema is an empty object with additionalProperties: false, so harness/agents/rosie/plugins/supplier-events/config.json can only be {}.
  • Secret: SUPPLIER_EVENTS_APP_SECRET, required. Bucket path rosie.supplier-events.SUPPLIER_EVENTS_APP_SECRET. scripts/app/secrets.sh reuses an existing value or generates a random one, writes it to Rosie's bucket, and adds the same name to app/.env.local. It runs only when app/.env.local exists and never rotates the value by itself.
  • Why its own secret: the caller is the Next.js app, not an in-harness process, so the boot-time COGNISPHERE_WEBHOOK_SECRET isn't available to it. The artifacts plugin uses the same split.
  • Start and stop: start(ctx) stores the context and logs supplier-events started — inbox at /webhook/rosie/supplier-events/notify. stop() clears it, and later requests get 503. No timers, files or seeded scripts; the only seed is the prompt fragment.
  • Failure: without the secret the plugin fails to start and Rosie runs without it. Every app POST then gets a non-2xx answer, which the app logs and ignores.

Web Chat (webchat)

Web Chat is the chat channel behind the app's agent panel and the supplier portal's chat. It stores one transcript per conversation in Supabase, wakes the agent on that conversation, and takes the agent's replies. Manifest description: "Browser chat channel, one transcript per thread." It is enabled on Rosie, Daisy and Nova. This section covers the plugin itself; Chat and live updates covers the browser and app side end to end.

Conversations (thread ids)

ThreadMeaning
mainThe agent's general conversation, shared with Telegram's main route, so the panel's Main and Telegram are one conversation
jr-<id>One job request (Rosie)
supplier-<slug>One supplier company. The same string names two separate conversations: Rosie's (rosie_thread_id) and Daisy's (daisy_thread_id). On Rosie it is one conversation that every job shares; a job's supplier tab is that conversation filtered to the job.
customer-<slug>One customer, across all their jobs (Rosie), shared the same way

Shared supplier and customer conversations (Rosie)

With partyRouting on (Rosie only), a supplier's or customer's conversation is one transcript per company that all jobs share. Every message records who sent it (sender_kind), the agent thread it belongs to (origin_thread_id: jr-<id> or main) and its job (job_request_id).

  • Portal messages wake the party's own thread (supplier-<slug>), with the last 20 messages and the supplier's active jobs as context. That thread does one thing: it calls webchat-cli route to tag the message with its job and deliver it to the job thread or threads that own it (or main).
  • Team messages typed in a job's supplier or customer tab are for the party. They are stored as portal-visible LPS messages, so a partner sees them in the portal; a party without a portal only has them recorded. Rosie hears of them silently, on the party's own thread (web_message_silent), and nobody is owed a reply.
  • The panel shows a party conversation the way the party sees it: their own messages plus LPS's party-visible ones, across all jobs, or one job with job=<id> (a tab's "JR-<id> only" switch).
  • Email traffic can be logged into the conversation with webchat-cli send --log-as, so a job's tab shows the whole exchange.

Storage

  • Transcripts live in Supabase tables threads (one row per agent and thread id) and thread_messages (seq, role, text, files, sender_name, portal, created_at), from migration 0078. Migration 0147 added sender_kind (lps, agent, supplier or customer), origin_thread_id and job_request_id (set to null when the job is deleted). A row from before 0147 with no sender_kind is read from its role and portal flag. If a message names a job whose row doesn't exist yet, it is stored untagged and migration 0148 tags it when the job row is written. The plugin is the only writer of messages. See Database schema.
  • On threads the plugin writes web_read_id, portal_read_id and pending_since. A trigger keeps the last_* preview columns, which the plugin clears on reset.
  • RPC link_thread(p_agent, p_thread_id) upserts the thread row and returns its id. It is called on every write and never cached, because deleting a job can remove its thread row.
  • A write-through memory cache holds the newest historyLimit messages per thread. Every read is served from memory.
  • File bytes stay on disk. Uploads go to agents/<id>/plugins/webchat/inbox/ and agent attachments to …/state/outbox/. Only metadata goes to the database.

Events sent to the agent: web_message and web_message_silent

Both api/send and api/app-send emit web_message, with threadIdOverride set to the thread id and channelId set to web or portal. A team message on a party thread (with partyRouting) is emitted as web_message_silent with isSilent, so it informs the party's thread without waking it and raises no working flag. api/route re-emits a routed party message as web_message on each target thread.

  • Text: what the user typed, then one <label>[plugins/webchat/inbox/<stored>] line per attachment, then an Additional context: block when there is any: the browser's current page (- Current page: <title> (<path>)), and on routed or party messages the conversation and message id, routing notes, or the party history and active jobs. The saved transcript keeps only the typed text. The page must be a path starting with / (not //), otherwise it is dropped. The path is cut to 500 characters and the title to 200.
  • Metadata: SenderName, SenderKind, MessageId and WebchatThreadId always, and JobRequestId when the message is tagged with a job. Team messages add OriginThreadId and OriginChannel: web, so approvals can find their way back to the chat where they were asked. Portal messages add the server-verified SupplierId and SupplierName and carry no origin fields. Attachments and Page appear when present. A team message can't spoof supplier identity: any client-sent supplier fields are ignored.
  • After a successful non-silent notify the plugin raises the thread's working flag (pending_since).

What suppliers can see

Only party-visible messages cross to the supplier

A supplier sees three kinds of message: what they typed in the portal, agent replies sent with webchat-cli send --portal or ask --portal, and, on Rosie, messages the team types in a job's supplier tab, which are sent as LPS. Everything else on that supplier's conversation (internal notes, relays, approval requests, logged emails) stays internal. The prompt fragment allows --portal only on an approved reply to the party, or to record mail Rosie sent them.

Read cursors and the working indicator

  • Each thread has two read cursors, stored as threads.web_read_id (team) and threads.portal_read_id (supplier) and mirrored in memory. A cursor only moves forward.
  • The team cursor moves on messages?read=1, send and read. The supplier cursor moves on app-messages?read=1 and app-send. An agent reply moves neither, because it is what the unread dot exists to announce.
  • The working flag lives in memory and in threads.pending_since. It expires in memory after pendingTimeoutSec, is cleared by api/reply, and is cleared for the whole agent at plugin start. It now feeds only the portal's pending (api/app-messages); the team panel's pending comes from the harness's in-flight events on that thread.

Deleted job chats (Rosie only)

When a job request is deleted, the database writes a permanent tombstone to deleted_job_threads. On Rosie's plugin only, purgeDeletedJobChats reads those tombstones 1,000 rows at a time, drops the thread from memory, asks the harness to reset that conversation, and stamps purged_at. If the harness refuses because a turn is running, the row is retried on the next pass. The sync runs at start, before every HTTP request, and every 15 seconds. A tombstoned thread throws "This job chat has been deleted", which the plugin returns as 410. The app doesn't call api/reset on delete; the plugin reconciles from the tombstones.

CLI: scripts/webchat/webchat-cli

  • send --text "…" [--file <path>]… [--thread-id <id>] [--portal] [--job <id>]
  • send --log-as supplier|customer --sender "<name>" --thread-id <party thread> --text "…" records a party's email in their conversation. It wakes nobody and never reaches a portal.
  • ask --questions-file <path.json> [--thread-id <id>] [--portal] [--job <id>] posts an interactive multiple-choice card
  • route --thread-id <party thread> --message <id> --to jr-<id>|main [--to …] [--note "…"] posts to api/route. --to can be repeated or comma-separated, up to 5.
  • --self-check

The default thread is $PI_THREAD_ID, the thread the agent is working on, and that thread is always sent as the message's origin. --job defaults to the job of a jr-<id> origin, so a job thread's messages into a supplier conversation are tagged with that job. The inbox is $HARNESS_BASE_URL/webhook/$PI_AGENT_ID/webchat when that is set, otherwise $PI_WEBHOOK_BASE/webchat, and the CLI exits with an error if neither is set. It posts to api/reply with x-webhook-secret. A non-200 answer prints webchat send failed (HTTP <code>) and exits 1.

Questionnaire rules (questions.ts): a title of at most 200 characters, 1 to 20 questions of at most 1,000 characters each, 1 to 10 distinct options of at most 300 characters, and an optional multiSelect. A literal "Something else" option is removed, because the UI always adds a free-text box. The card is stored in thread_messages.text as Questionnaire: <title>, a webchat-questionnaire:v1 marker and JSON with a fresh UUID. Answers come back as one user message starting Answers to questionnaire <uuid>.

Prompt fragment

Lifecycle and failure

  1. Secrets. Both Supabase secrets are required; without them start throws and the plugin fails.
  2. Setup. Creates the Supabase client (no session persistence) and the inbox and outbox directories, and derives the harness API base from ctx.httpBaseUrl. If that is missing it logs an error and every browser request is refused.
  3. Warm the cache. Loads every thread for this agent that has messages, with its newest historyLimit messages and both cursors. A database error here fails the plugin.
  4. Reset state. Clears pending_since, because a restarted harness isn't mid-turn.
  5. Background work. Runs the deleted-job sync and starts its 15-second interval, then deletes unreferenced portal-* uploads older than one hour (also done on each portal upload and send). On Rosie, a database error in this first sync also fails the plugin. Later interval failures are logged as webchat: deleted job cleanup failed.
  • stop clears the interval, waits for a running sync, and drops the context.
  • Write semantics: the message insert must succeed before a send is acknowledged, and the agent is woken only after it does. Cursor and working-flag writes are fire-and-forget; failures are logged as webchat: threads update failed and the in-memory copy stays authoritative.

Google Workspace (gws)

The gws plugin connects an agent to its Google mailbox. It polls Gmail on a timer and sends the agent one short notification per new message. The agent reads the full message, attachments included, and sends or replies by running the gws command-line tool itself. Manifest description: "Gmail polling via the gws CLI. One notification per inbound message; the agent sends/replies by calling gws directly."

Why there is a local copy

harness/plugins/gws/ is a fork of the plugin bundled with harness 0.12.0, and it shadows the bundled one. Its manifest must stay identical to upstream, which plugin-compat.test.mjs checks, along with the fact that the user-space copy is the one selected. The local changes:

  • Collision-safe attachment file names
  • A download directory that refuses to overwrite files or follow symlinks, pinned through a file descriptor
  • The scripts/gws/email CLI is run directly, not through bash
  • Tests: attachment-files.test.mjs, attachment-files-security.test.mjs and plugin-compat.test.mjs

Who has it

  • Rosie: enabled but passive (pollIntervalSec: -1), so it never polls the mailbox and sends no mail notifications. Start still checks sign-in and reads the mailbox profile. Her mailbox has to be connected through the console (Settings → gws → Sign in with Google), and polling then turned on. A deployment check on 2026-09-10 found her credentials secret missing. While it is missing, the plugin fails at start and Rosie runs without it.
  • Daisy: polls every 300 seconds with a custom unread-inbox query. Per-supplier routing rules (about a hundred) send each supplier's mail to that supplier's thread. The catch-all rule router-all sends everything else to her router thread and must stay last.

Secret

GOOGLE_WORKSPACE_CLI_CREDENTIALS_FILE, required. It is a path to a credentials file written by the console's per-agent "Sign in with Google" flow. The plugin passes it to the gws subprocess with GOOGLE_WORKSPACE_CLI_KEYRING_BACKEND=file.

Endpoints

None. The plugin has no handleHttpRequest. The Google OAuth endpoints (/api/gws/oauth/*) belong to the harness console.

Lifecycle: start, poll, stop

  1. Read config. Base config plus the overlay.
  2. Check sign-in. The secret must be set, the file readable, and gws auth status must succeed. A missing binary fails with "gws CLI not found on PATH".
  3. Find the mailbox. gws gmail users getProfile must return an address.
  4. Announce settings 5 seconds later. Plugins start before the runner, so an earlier notify would be dropped.
  5. Tick. A self-rescheduling timer, so ticks never overlap. Each tick reloads settings and, unless passive, polls. Errors log "gws poll tick failed; will retry next interval".

A poll reloads state/routes.json (keeping the previous rules if it can't be read), lists matching messages 50 at a time through every page, and handles each Gmail thread once:

  • The thread's messages are sorted by date, and the subject is frozen at the first message.
  • The harness thread id is the first matching route's threadId, otherwise <Subject>[<gmailThreadId>] (subject sanitized and capped at 120 characters, with (no subject) as a fallback).
  • Default mode: only the newest message is considered. It wakes the agent if the sender is allowed and, when requireAgentInTo is on, the agent is in To.
  • Backlog mode: every allowed message is emitted, but only the thread's first message wakes the agent. The thread is then added to state/ingested-threads.jsonl.
  • All payloads are built first and then emitted together, so one thread's rows batch into one turn.
  • Every unread message in the thread is then marked read. That is how default mode avoids notifying twice.

stop sets a stopped flag and clears both timers.

Attachment downloads

Files go to plugins/gws/inbox/<MessageId>/ as <n>-<safe ASCII name, at most 160 bytes>, each followed by an Attachment: {…} JSON line with originalFilename, contentId, mimeType, partId, attachmentId, filename, path and status (downloaded or failed). Files are created exclusively with mode 0600. An identical existing file is reused and a different one counts as a failure. The pinned-directory technique needs Linux /proc, so on other systems downloads fail closed with "secure attachment downloads require Linux procfs". They work on the production server but not on a macOS development machine.

Prompt fragment

plugin-gws.md says that email_received wakes and email_silent is context only, explains the metadata, says to read a message before acting, points to the three skills, says the agent owns its settings and re-asserts them when gws_settings arrives, and asks for plain-text bodies (--html for formatting). Nothing is sent until +send or +reply runs. After an error, the agent checks in:sent newer_than:1d before sending again.

Failure handling

  • At start: a missing or unreadable credentials file, a missing gws binary, a failed auth status or no profile address each throw. The plugin is marked failed and the agent keeps running.
  • A tick error is logged and the next tick goes ahead.
  • A per-thread error is logged. The thread stays unread, so it is retried on the next tick.
  • A mark-read failure only warns. The message stays unread and is sent again on the next poll, so the agent can be woken twice for one email.
  • A backlog ledger write failure warns "thread may be re-emitted".

admin (core)

  • Purpose: the admin chat channel in the harness web console. The human admin reads the agent's visible turn text directly. Agents use it when they are stuck, need a permission, or face a major change.
  • Agents: all four, always on. No config, secrets or CLI.

scheduler (core)

  • Purpose: timed wake-ups. A schedule fires a schedule_fire event with metadata ScheduleName and Cron.
  • CLI scripts/scheduler/scheduler-cli:

  • Cron has 5 or 6 fields, in the harness timezone (America/Chicago). --thread-id {{ThreadId}} returns to the current thread. --channel defaults to the schedule name.
  • State: plugins/scheduler/state/schedules.json. The plugin watches the file, and changes apply in about a second.
  • Agents: all four. Daisy's daily 9 AM check-in (0 9 * * *, thread daily-9am-checkin) is the only active schedule in the checked-in state. Her other entries are paused, either daily jobs or one-shot schedules on supplier threads that applied future-dated supplier lists on their effective date and have already fired. agent-messaging (core)

  • Purpose: agents hand work to each other and to their own task threads.
  • Endpoint: POST /webhook/<to-agent>/agent-messaging/api/send with X-Webhook-Secret: $COGNISPHERE_WEBHOOK_SECRET. Body {from_agent, from_thread_id, thread_id, message, silent, subject?}. The sender identity comes from the harness-set $PI_AGENT_ID and $PI_THREAD_ID, so it can't be spoofed.
  • Responses: 401 for a bad secret, 403 when the sender isn't in allowMessageFrom (don't retry), 404 for an unknown agent or a plugin that isn't running. "could not reach … inbox" means the harness is down.
  • Config: allowMessageFrom, default ["*"]. No agent restricts it.
  • Event: agent_message, with metadata From, FromThread and Subject, plus IsSilent when sent with --silent.
  • CLI: scripts/agent-msg/send --to-agent --thread-id --message [--subject] [--silent] [--self-check]. A thread id that doesn't exist yet starts a fresh thread, which is how task threads (<ThreadId>-§-[TASK]-§-<slug>) are created.
  • Agents: all four.

telegram (catalog)

  • Purpose: each agent's Telegram group. The plugin long-polls a bot from the server, so there is no public webhook.
  • Config: pollTimeoutSec (25 here) and allowedChatIds, which locks each agent to its own group chat. Secret: TELEGRAM_BOT_TOKEN. Without it the plugin logs "TELEGRAM_BOT_TOKEN not set; telegram plugin disabled" and the agent still starts.
  • Inbound metadata: Channel (chat id), SenderId, SenderName, MessageId, EventType (message or edit), ReplyToMessageId and MediaGroupId. Media is saved to plugins/telegram/inbox/. /reset is handled by the plugin itself and never reaches the agent.
  • CLIs: scripts/telegram/telegram-cli (send-message, send-file, edit-message, delete-message, send-reaction; Markdown is converted to Telegram HTML) and scripts/telegram/routes add | list | remove for state/routes.json. Chat patterns are anchored regexes, the first rule wins, and rules are re-read every batch. Skill: route-chats.
  • Routing: every agent has one route sending its group to thread main. Without it, messages would land on a thread called default, even under the single strategy.
  • Agents: all four. Lily is reachable only here.

artifacts (catalog)

  • Purpose: publish one self-contained HTML page with a private or public link on the app's domain. No inbound events.
  • CLI scripts/artifacts/artifact: publish <file.html> [--slug] [--public], share <slug> --public|--private, list, url <slug> [--private] and rm <slug>. Files are stored as plugins/artifacts/state/<slug>.<public|private>.html. Skill: publish-artifact.
  • Serving: the plugin serves /webhook/<agent>/artifacts/<public|private>/<slug> (plus /meta). The app proxies it at /a/<agent>/public/artifacts/<slug> and /a/<agent>/private/artifacts/<slug>, sending the x-artifacts-secret header. Slugs match ^[a-z0-9][a-z0-9-]{0,63}$. Private pages need a signed-in admin. Pages are served under a CSP sandbox, and no token ever appears in a URL.
  • Config: appBaseUrl, per agent (<app origin>/a/<agent>). Secret: ARTIFACTS_APP_SECRET, shared with the app; without it the private path answers 401. The app's allowlist of agents is the env var ARTIFACTS_AGENTS.
  • Rule: private by default. Agents use --public only for content that is fine for the whole internet.
  • Agents: Rosie, Daisy and Nova.

Known discrepancies

Where older docs or comments disagree with the code, this page follows the code. These are the differences found while writing it.

ClaimWhat the code does
docs/harness/README.md: two user-space plugins, no catalog plugins forkedThree directories in harness/plugins/, and gws is a fork
docs/harness/rosie-setup.md: "AR draft/submission notifications"Drafts emit nothing and plain saves are dropped. Only submissions and order events are delivered.
plugin-supplier-events.md doc: metadata lists only the availability fieldsOrder events also carry OrderId, OrderChanges, OrderStatusChanges, OrderItemId and OrderItemStatus
Plugin header comment and docs: order_status_updated is part of the flowThe plugin accepts it, but no app route sends it. The portal uses order_status_saved.
Rosie's supplier-coordination skill describes handling availability_updatedThat event is never delivered, so the guidance is unused
docs/harness/plugin-webchat.md: "two callers, two mechanisms"; the in-flight check forwards the browser cookieThree mechanisms. The plugin forwards whatever auth headers came in, which for the app is the bearer plus X-App-User.
docs/harness/plugin-webchat.md: config threadId is where web messages are deliveredIt is only the default; an explicit threadId wins
Web Chat docs don't say the deleted-job sync is Rosie-onlydeleted-job-chats.ts returns early for every other agent
gws header comment: thread id <Subject> [<id>] with a space<Subject>[<id>], no space
scripts/gws/settings set --poll-interval-sec says values must be at least 10It accepts 0 to 9; the plugin raises them to 10
Scheduler prompt: --once pauses the schedule after it firesscheduler-cli help says it is deleted after its first firing (the CLI writes onetime: true). The library source isn't in this repository. The checked-in schedules.json files, though, keep fired one-shots with paused: true, which matches the prompt, so the CLI help is the stale one.

A smaller note on Web Chat: api/reset starts the harness context reset without waiting for it, so the transcript is wiped even if the harness later refuses.
