Agents (technical)

LPS runs four AI agents, Rosie, Daisy, Lily and Nova, inside one server program called the Cognisphere harness. This page describes how the harness runs them and how each agent is configured: its instructions, skills, tools, channels, the data it may change and the approvals it must get.

EngineersTechnicalReference~30 min read

In short

If you read only this section, these are the main points:

  • One harness, four agents. The harness is a single Node.js server. It hosts every agent, keeps a durable queue of incoming messages for each one, and starts a language-model process to handle each batch of messages.
  • Each agent is a folder. An agent is the directory harness/agents/<id>/. That directory holds its settings (agent.json), its instructions (system_prompts/), its step-by-step procedures (skills/), its tools (scripts/), its reference material and memory (knowledge/), and its working notes (workspace/).
  • Plugins are the doors to people. Every inbound event and every message to a person goes through a plugin: the in-app chat, Telegram, Gmail, timers, agent-to-agent messages and page publishing. Anything an agent writes in its own turn stays internal until a plugin command sends it. The exceptions are tools, not channels: Rosie and Daisy reach the database and file storage through their own scripts, and every agent can search and browse the web.
  • Every conversation is a thread. Examples are one thread per job (jr-42), one per customer and one per supplier. Threads share the agent's knowledge and skills, but their conversations stay separate.
  • Roles are split. Rosie runs jobs, quotes, availability requests and orders. Daisy runs suppliers, price lists and inventory. Lily turns Chris's feedback into requirements. Nova changes the code and deploys the app.
  • Safety is built in. No customer or supplier email goes out without Chris's yes to the exact draft. Orders need the customer's commitment. The agents' database tool refuses DELETE and schema-changing statements (it allows only creating or replacing functions). An agent never invents prices, names or dates.

How the harness is built

The harness is the npm package @cognisphere-sh/cognisphere-harness, pinned at version 0.12.0. It runs from the data directory harness/. harness/harness.json holds the deployment version and the timezone (America/Chicago), which is used for schedules and daily notes. In production it runs as cognisphere serve --port $HARNESS_PORT (default 3142) under systemd. The app reaches it at http://127.0.0.1:<port>, and nginx publishes its operator console under a separate host name. See Deployment and operations.

What happens when a message arrives:

  1. A plugin receives something. Examples: a chat message in the app, a Telegram post, a new email, a schedule firing, or a message from another agent. The plugin calls notify with the text, a channel id and optional metadata.
  2. The harness queues it. The event is written to the agent's durable queue (sessions/.events.db, a SQLite file) and mapped to a thread id.
  3. A slot picks it up. Each agent can work on several threads at once, up to its maxConcurrentSlots. Events that arrive for the same thread are batched together. If a run is already live on that thread, a new event can steer it.
  4. A model process is spawned. The harness assembles the system prompt, rebuilds the skills list, and starts the model runner (pi, from @earendil-works/pi-coding-agent) with the agent directory as its working directory. The conversation history for the thread is loaded from sessions/<threadId>/.
  5. The agent works. It reads files, runs its scripts (database helpers, plugin CLIs) and writes notes. Nothing reaches a person until a plugin CLI sends it.
  6. On failure it retries. A delivery that failed or was interrupted is redelivered marked Retry: true; maxAttempts in agent.json caps the attempts. A turn cut off by a harness restart is requeued and resumes when the harness comes back.

How the app talks to the harness

The browser never calls the harness directly. The Next.js app's server calls it with Authorization: Bearer <app secret> and an X-App-User header naming the signed-in admin, and only after the app's own session check. Plugins with their own HTTP endpoints authenticate their callers themselves: the supplier-events plugin checks X-App-Secret, the webchat portal endpoints check their own app secret, and agent CLIs inside the harness use a per-boot webhook secret. Details are in Chat and live updates, Auth, roles and security and Harness plugins.

The library is read-only here

node_modules/@cognisphere-sh/cognisphere-harness is never edited in this repository. Changes that need new harness capability go upstream. Version bumps go through the cognisphere-upgrade skill. LPS-specific behaviour lives in the agent directories and in the user-space plugins under harness/plugins/.

Threads, sessions and task threads

A thread is one conversation and one routing identity. All of an agent's threads share its workspace, knowledge, memory and skills. Each thread has its own conversation history, and content must not leak from one thread to another unless someone asks for it.

How a message finds its thread

  • threadIdStrategy gives the default. Rosie and Daisy use plugin_channel, so each plugin and channel pair becomes its own thread unless a plugin says otherwise. Lily and Nova use single.
  • threadIdOverride on a plugin event wins over the strategy. The webchat plugin sends the thread the user has open (main, jr-12, supplier-<slug>, customer-<slug>). The supplier-events plugin sends the supplier's thread.
  • Routing rules in Telegram (plugins/telegram/state/routes.json) and Gmail (plugins/gws/state/routes.json) map a chat or a sender to a thread. The first matching rule wins.
Why every agent has a Telegram route to main

single does not by itself produce a thread named main. Without a route, Telegram messages landed on a thread called default. All four agents therefore carry one Telegram route, main → thread main. The webchat plugin's default thread is also main, so the app chat panel and Telegram share one main conversation per agent.

Sessions

sessions/<threadId>/ holds the thread's conversation history as JSONL files and the .system-prompt.md assembled for the latest spawn. sessions/.events.db is the agent's event queue and log; an event being processed has status in_flight, which the app chat uses to show "working". Agents read old transcripts with the paginated scripts/agent/session-reader. A /reset in Telegram, or Reset in the app chat, clears that thread's context.

Task threads

A task thread is a fresh-context sub-thread. An agent starts one by messaging itself through agent-messaging on the thread id <ThreadId>-§-[TASK]-§-<task-slug>. The base prompt says "delegate aggressively", but each LPS prompt sets its own, narrower rule:

AgentTask-thread rule
RosieDo the work in the owning thread. Use a task thread only for a big one-shot read.
DaisyOne task thread per supplier email that needs parsing. It finishes everything itself (labels, panel close, daily note, any effective-date schedule) and sends one silent report at the end.
LilyOnly substantial write-ups, so main stays free for conversation.
NovaOne builder task thread per change, plus one fresh visual-review thread for UI work.

Daisy's and Nova's prompts also forbid a task thread (Nova's builder) from starting task threads of its own.

Events, metadata and the communication model

Every inbound message starts with a <harness-metadata> block. The harness always sets Timestamp, Plugin, Channel and ThreadId, and adds IsSilent: true, Retry: true or Continuation: true when they apply. Plugins add their own fields, rendered in PascalCase. The notify event name is not shown to the agent, so a plugin that emits several kinds of event on one channel adds an EventType field (Telegram and supplier-events do).

Before each model call the runtime inserts a Checkpoint: <n> / CheckpointTokens: +<delta> message, and the newest message ends with Model: and ContextUsage: <used>/<window>. These are informational.

The communication model

An agent's turn text is internal. Nothing reaches a person until a plugin CLI runs: webchat-cli send, telegram-cli send-message, gws gmail +send and so on. The one exception is the admin plugin, whose channel is the harness console: there the human admin reads the visible turn text. Agents use it when they are stuck, need permissions, or want to flag a major change.

Portal visibility

In the webchat plugin, only a reply sent with --portal is visible to the supplier in their portal. Internal notes, relays and approval requests never use --portal, even when they sit on the same supplier thread.

Who may edit 1-agent.md

The base prompt requires admin approval for edits to 1-* files. Rosie's, Daisy's and Lily's prompts define that approval: explicit feedback from Chris (or, for Rosie and Daisy, the developer) authorizes the change immediately. Changes inferred from implicit feedback are proposed first and applied only after approval.

The agent directory is not auto-refreshed

Because 0.1-agent-directory.md is generated only when missing, each agent's roster can describe its teammates differently. Some rosters still carry older one-line descriptions of Rosie and Daisy. Each agent's own agent.json and 1-agent.md are the current statement of its role.

Skills

A skill is a versioned, step-by-step procedure: the agent's procedural memory. Every repeatable procedure belongs in a skill, not in a prompt file, knowledge file or workspace note.

  • Layout. skills/agent/<slug>/SKILL.md with frontmatter name and description, a CHANGELOG.md, and optional scripts/ and artifacts/ directories inside the skill. Relative paths in a skill resolve against the skill's own directory.
  • Versioning. The semver appears in the description, as (vX.Y.Z), and in metadata.version. A correction is a patch, changed or added steps are a minor bump, an incompatible rewrite is a major bump. Each bump gets a changelog entry.
  • Discovery. The <available_skills> block is rebuilt on every spawn, so changed skills need no restart. When a skill the agent already read changes version, the skill-update-notice extension sends a one-time SystemMessage.
  • Plugin-owned scopes. skills/<plugin-id>/ is reseeded from the plugin on start and never edited by hand. Shipped here: artifacts/publish-artifact, gws/read-email, gws/search-email, gws/route-email, telegram/route-chats.
  • Task-menu style. Rosie's, Daisy's and Lily's larger skills use SKILL.md as a short menu and keep the detail for each task in artifacts/<task>.md, so an agent loads only the step it needs.
  • Names, not versions. All four LPS prompts override the base prompt here: skills are named without version numbers in handoffs, briefs, prompts and docs. The version in the skill's own frontmatter is the authoritative one.

Each agent's skills, with current versions, are listed in its section below. The create-skill skill, present on every agent, says where each kind of feedback goes and how to author or bump a skill.

The database guard (scripts/agent/supabase/query)

Rosie and Daisy reach the database only through this script. It is a Node wrapper around psql that maps the agent's Supabase secrets to Postgres connection variables without putting the password on the command line. It connects through Supabase's session pooler and falls back to the direct host if that connection fails.

Allowed statementsRefused statements
Statements starting with SELECT, INSERT, UPDATE, WITH, EXPLAIN, VALUES, SET, SHOW, transaction control (BEGIN, START, COMMIT, ROLLBACK, SAVEPOINT, RELEASE), and CREATE [OR REPLACE] FUNCTION|PROCEDUREAny statement containing DELETE, DROP, TRUNCATE, ALTER, GRANT, REVOKE, COMMENT, REASSIGN, COPY, DO, IMPORT, LOCK, LOAD, PREPARE, DEALLOCATE, EXECUTE, CALL, LISTEN, NOTIFY, UNLISTEN, CHECKPOINT, DISCARD, the maintenance commands VACUUM, REINDEX, CLUSTER and REFRESH, and every other CREATE form (table, index, view, trigger…)

The keyword scan runs after comments and quoted text are masked, so a forbidden word inside a note does not trip it, while one hidden in a CTE still does. Function bodies are masked too, so the guard does not check what a function created this way does when it runs. Rosie's and Daisy's copies share the same allow and deny lists but mask text with slightly different code; Daisy's copy has an offline test (query.test.mjs).

In practice the agents cannot run DELETE or change tables, indexes or permissions through this tool. Removing something goes through an RPC that does a soft delete (for example delete_candidate) or an is_active = false flag. Schema changes are SQL migrations applied by the developer.

Bootstrap, extensions and plugins

Bootstrap

bootstrap/bootstrap.sh prepares an agent's runtime and runs on every agent start. It is idempotent and non-interactive, and identical on all four agents. It:

  1. Re-asserts execute bits on every shebang script under scripts/.
  2. Installs system tools best-effort: ffmpeg and pdftoppm (poppler).
  3. Creates the Python virtualenv .venv and installs bootstrap/requirements.txt. All agents get markitdown[…]==0.1.5 and ddgs. Daisy also gets pillow and pillow-heif for converting HEIC photos.
  4. Pins the model runner: installs the global pi at PI_VERSION (default 0.84.4) if the installed version differs.
  5. Installs agent-browser (npm global) with its Chrome build.

Plugins in brief

Plugins come in three kinds. Core plugins (admin, scheduler, agent-messaging) are bundled and always on. Catalog plugins (telegram, gws, artifacts) are enabled per agent by creating harness/agents/<agent>/plugins/<id>/, optionally with a config.json. User-space plugins live in harness/plugins/<id>/: here webchat and supplier-events, plus gws, a hardened fork that shadows the bundled one. On every start a plugin copies its seed/ tree (prompt fragment, scripts, skills) into the agent directory. A plugin that fails to start is recorded as failed, and the agent keeps running.

Scheduler and schedules

The core scheduler plugin fires cron schedules into a thread as a schedule_fire event carrying ScheduleName and Cron. Cron expressions have 5 or 6 fields and use the harness timezone (America/Chicago). State lives in plugins/scheduler/state/schedules.json; the plugin watches the file, so changes apply within about a second.

The ingestion pipeline

How a supplier's list becomes inventory. The business view is in Suppliers, plants and catalogue.

  1. Arrive. Post an arrival block on the supplier's panel and run ingest-context --thread <ThreadId> (read-only: company, locations, known quirks from suppliers.notes, the five newest sources).
  2. Identify the receipt. source-check fingerprints the file and skips a list that hasn't changed.
  3. Assign locations for each part of the list.
  4. Read the list page by page into /tmp/<thread>-p<N>.json.
  5. Match. match-candidates --supplier <id> --entries … --plan … returns up to five active rows plus the best inactive row by trigram similarity. Read-only; its suggestions are a sort aid only.
  6. Write. Upload the file and create inventory_sources rows. apply-plan <plan.json> is a dry run until --commit. Actions: update, reactivate, insert (requires "searched": true), park. It sets only the name parts (common_name, botanical_name, cultivar_variety_trade_name), size, price, quantity, dimension, note and image columns, never the composed name, *_key columns, ids or timestamps. All row counts must match the plan or the whole transaction rolls back.
  7. Check. Compare with the original and run qa-check --source <uuid> (read-only).
  8. Photos in the email go to the plant-photo-catalogue skill.
  9. Finish. Gmail label Daisy plus exactly one of Daisy/Catalogued, Daisy/Failed, Daisy/Not Availability or Daisy/Escalated; close on the panel with one or two sentences and numbers; write the daily note; retire older, empty, superseded sources; schedule a one-shot if the list takes effect later.
Ingestion rules

The newest source wins for what it states. Silence is not a value: a plant missing from a new list is not marked unavailable. No inventory row is retired during an ingest. The email body beats its attachment. Supplier item codes are the best match key.

Shipping a change

A requested change should normally be live the same day. A person saying "deploy", "push to live" or "do it" is the authorization.

  1. One builder. The whole request goes to one task thread, which edits, checks, deploys and reports. A trivial fix she may do herself.
  2. Edit on main in the primary checkout, with no worktrees. Unrelated uncommitted changes are left alone; she stages only her own paths.
  3. Check. pnpm --dir app typecheck plus the relevant test files (pnpm --dir app exec tsx --test <file>). The full suite is not run on the server, which lacks the memory for it.
  4. Visual check for UI changes with the visual-ui-release-qa skill. A FAIL blocks the deploy.
  5. Deploy. Commit, then sudo ./scripts/server.sh restart app, which builds the app and restarts only the app service.
  6. Report once on the requester's channel: what changed, the commit, and that it's live, with a screenshot for UI work. Rollback is git revert <sha> and the same restart.

Only one memory-heavy step (typecheck, preview build, app build or browser) runs at a time. She stops and asks only when a check, the build or the visual review fails twice; when the change touches the database, workflows or secrets, or needs a harness restart; or when the request is ambiguous. Only a person can add a new gate or approval stage. Status updates are one or two plain sentences.

Nova never restarts the harness

Nova runs inside the harness. Restarting it would kill her own process mid-turn, so harness changes (agent.json, plugin config, prompts, including her own) are applied by the operator with sudo ./scripts/server.sh restart. Her interrupted turn is requeued and resumes when the harness comes back.

Handoffs between agents

Agents hand work to each other with scripts/agent-msg/send. The receiver gets an agent_message event whose From and FromThread are set by the harness. Sending to a thread id that doesn't exist yet starts a new thread. No agent restricts who may message it (the default allowMessageFrom is ["*"]). A 403 means the sender is not allowed, a 404 means an unknown agent or a stopped plugin, and "could not reach … inbox" means the harness is down.

A teammate's message is never approval

Handoffs move work, not permission. A message from another agent can carry Chris's words as evidence, but the agent that sends something to a customer or supplier still checks that Chris approved that exact draft.

Size limits and checks

python3 scripts/check-agent-instructions.py enforces the instruction budget and consistency for Rosie, Daisy and Lily (Nova is not checked):

  • at most 6,500 characters per skill entry file (SKILL.md);
  • at most 400 characters per skill discovery description, which must carry the current version;
  • at most 6,500 characters across an agent's 1-* prompt files combined;
  • valid frontmatter and skill names, a changelog entry for the current version, no broken local links or numbered section references, Python helpers that parse and are executable, and no drift between Rosie's and Daisy's shared helpers (schema, daily-note, index-add).

The September 2026 rewrites of Rosie, Daisy and Lily cut their deployment-owned prompts by about two thirds and their skill entry points by almost 90% (measured in characters), moving detail into per-task artifacts. Smoke tests must never send fake business messages or change live data. A harness-side change counts as done only when a restart comes up clean: every agent running and no failed plugins.
