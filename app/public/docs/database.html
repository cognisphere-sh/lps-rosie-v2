Database schema

All of LPS's business data lives in one Supabase (PostgreSQL) database. The web app and the AI agents read and write that same database. Many business rules are built into the database itself, so they apply no matter who makes a change.

EngineersTechnicalReference~30 min read

In short

If you read only this section, these are the main points:

  • One database for everything. Suppliers, plants, photos, customers, jobs, availability requests, orders, user accounts and chat transcripts are all stored in one hosted PostgreSQL database run by Supabase. The web app, Daisy (the agent who catalogues supplier availability) and Rosie (the agent who runs customer jobs and works with suppliers) all use it.
  • The data falls into a few areas. The catalogue covers suppliers, their contacts, their plant lists and a photo library. The sales area covers customers, their jobs, the supplier options for each job line, availability requests and orders. Two smaller areas hold accounts (who can sign in) and chat (conversations with the agents).
  • Rules live in the database. Some examples: an availability request can never be deleted. A job can have only one availability request per supplier. When a job is Won or Lost, its requests close automatically. An order can never be for more than the customer asked for. Every change to a job is logged.
  • Screens stay current. The database announces changes to jobs, requests, orders, customers, suppliers and chats, and the app refreshes open screens straight away.
  • Changes to the structure are controlled. Each change to the database structure is a numbered SQL file (a migration) kept in the repository. Developers write and rehearse a migration, and then a human operator applies it. The agents' own database tool cannot create, alter or drop tables, indexes or triggers.
Source of truth

docs/supabase-schema.md is the source of truth for the live schema. It is a snapshot of the live public catalog, and Daisy's and Rosie's knowledge/files/SCHEMA.md files link to it. This page explains that schema. If the two disagree, trust docs/supabase-schema.md and the migration files, and fix this page. For changes after migration 0124, the migration SQL is the final word (see Where the schema doc lags).

Platform and access model

The database is PostgreSQL hosted on Supabase. It uses these extensions: pgroonga (full-text search indexes), pg_trgm (trigram prefilter for quoted searches) and moddatetime (keeps updated_at current through the handle_updated_at triggers).

Row-level security

  • RLS is enabled on every public table (0011_enable_rls.sql, 0020). Tables created later turn on RLS in the same migration that creates them.
  • The usual policy is "authenticated full access": FOR ALL TO authenticated USING (true) WITH CHECK (true).
  • threads, thread_messages and deleted_job_threads have RLS turned on and no policies, so only roles that bypass RLS can reach them.
  • Workflow RPCs are service_role only: REVOKE ALL … FROM PUBLIC, anon, authenticated; GRANT EXECUTE … TO service_role. Search and naming helpers can be executed by every role.
Pitfall

Never call signInWithPassword on the shared server Supabase client. If you do, later queries on that client run as authenticated rather than service_role, and RLS or the function grants refuse them. The login route checks passwords on a separate, throwaway client (see Auth, roles and security).

Conventions

  • Most primary keys are bigint GENERATED ALWAYS AS IDENTITY. The exceptions are suppliers.id (BY DEFAULT), inventory, inventory_sources and plant_photos (uuid DEFAULT gen_random_uuid()), app_users.id (the auth.users uuid), and the composite keys of order_item_job_request_items and deleted_job_threads.
  • Soft delete uses is_active boolean NOT NULL DEFAULT true. Availability requests are the exception: since 0127 they have no is_active column and cannot be deleted.
  • Most tables have created_at/updated_at timestamptz DEFAULT now(), and updated_at is kept current by the handle_updated_at trigger. Append-only tables (inventory_sources, job_request_changelog, thread_messages) have only created_at; order_item_job_request_items and deleted_job_threads have neither.
  • Status columns are text with a CHECK list, not PostgreSQL enums. The app maps the stored values to display labels (see Status values and labels).
  • Some constraint names predate a rename and were kept: the inventory primary key is plants_pkey, and its supplier FK is rate_charts_supplier_id_fkey.

Substitute model (0121–0124). When a supplier answers with a substitute, the asked row is stored as unavailable (quantity 0, price kept) with offered_candidate_id pointing at the substitute row. apply_candidate_offer then makes the substitute row Available (or Partial Qty if it is short) on the same AR. Stored diff_size_qty_sub rows are answers from before 0123, and the answer RPC refuses diff_size_qty_sub without a substitute. No status change alters a price (0122).

Triggers on candidates:

  • candidates_guard (BEFORE INSERT OR UPDATE of the content columns → guard_candidate_write()) refuses a write to a candidate whose AR is missing or closed, whose supplier differs from the AR's, or whose AR belongs to another job. The guard is bypassed when lps.line_sync = on (LPS line edits).
  • candidates_reopen (AFTER INSERT OR UPDATE OF availability_request_id → availability_request_reopen_on_new_line()): a candidate that joins a processing or submitted AR moves that AR back to new. Skipped while an offer or supplier answer is being applied.
  • candidates_processing (AFTER UPDATE → process_availability_answer()): any LPS content change resets a published AR (not draft or closed) to new and clears submitted_at. Skipped for supplier answers, submissions and offer application. Job-line sync edits (lps.line_sync) are not skipped, so they also return a published AR to new.
  • handle_updated_at.

Line ↔ candidate sync

A job line and its selected candidate are kept in step in both directions (0126, 0129):

  1. Candidate → line. select_candidate, and every AR submission, run apply_candidate_to_job_item. It copies the size, the price (0 becomes NULL), the availability (capped at demand, and left blank while unanswered), the derived status and the customer note onto the line.
  2. Line → candidate. The job_request_items_candidate_sync trigger (AFTER UPDATE OF status, available_quantity, unit_price, size, demanded_quantity, note_for_customer, when a selection exists and has not changed) writes the edit back to the selected candidate and then re-applies it. Statuses are mapped: pending ↔ NULL, need_to_order ↔ can_order, and alternative_proposed → diff_size_qty_sub on an original.
  3. Override promotes a substitute. If a line is set to Available or Partial Qty while a substitute is selected, the substitute becomes is_original. The same supplier's previous original is demoted to unavailable, offering the substitute (0129).
  4. These count as LPS edits. They run with lps.line_sync on: the edit is allowed even on a closed AR and never moves the AR to processing, but a published AR (new, processing or submitted) returns to new, as for any other LPS content change (0127).

Rules the database enforces

  1. One AR per job and supplier (0128).
  2. ARs cannot be deleted or truncated. To withdraw one, move it to Draft (0127).
  3. Suppliers cannot see drafts. The portal, public links and the answer functions all refuse them.
  4. When a job is Won, Lost, Archived or made inactive, its ARs close and their tokens are revoked. Reopening the job never reopens them.
  5. Every candidate must match its AR's supplier and job.
  6. An order cannot exceed the remaining customer demand or the supplier's availability, and needs explicit customer confirmation.
  7. Order tokens are revoked when the order closes or is deactivated. AR tokens are revoked in draft and closed.
  8. is_lps_partner is true exactly when the company has portal logins.
  9. Every supplier has a head branch, and branches never chain.
  10. Every insert or update of a job or job line is written to job_request_changelog.
  11. A deleted job's chat cannot be recreated.

Migrations

Every schema change is a numbered SQL file. The files make up the deployment's single, sequential record of schema changes, including changes to tables Daisy does not own.

Where they live

Numbering and file conventions

  • Each file name is a four-digit, zero-padded sequence number followed by a snake_case description, for example 0128_one_ar_per_job_supplier.sql.
  • Recent files wrap their work in BEGIN; … COMMIT; and most set SET LOCAL lock_timeout (often statement_timeout too). Files that add or change functions usually end with NOTIFY pgrst, 'reload schema' so the Supabase API picks them up.
  • New tables turn on RLS and set their grants in the same file. New workflow functions REVOKE from PUBLIC, anon, authenticated and GRANT EXECUTE to service_role.

Who writes and applies them

  1. Author. A developer or a coding agent writes the SQL, and tests under tests/ where it makes sense.
  2. Rehearse. The migration is run inside a live transaction that is then rolled back, or against a throwaway PostgreSQL loaded with the test fixtures. Row fingerprints, function bodies and grants are compared before and after.
  3. Apply. An operator applies it to the live database through the Supabase MCP or psql, at the developer's request. A few data-cleanup migrations ran through Daisy's guarded runner with explicit approval.
  4. Record and verify. The operator adds an entry to NOTE.md, updates docs/supabase-schema.md and docs/harness/daisy-migrations.md, then checks that the app's typecheck, build and tests pass and that the harness restarts cleanly.
Agents cannot migrate

Daisy's and Rosie's database tool (scripts/agent/supabase/query) uses a lexical guard that blocks DELETE, DROP, ALTER, TRUNCATE, grants and every CREATE except CREATE [OR REPLACE] FUNCTION|PROCEDURE. Table, index and trigger changes therefore always go through an operator. Function changes are possible through the tool, but they belong in a numbered migration like any other schema change. Routine supplier work never needs the migrations directory.

Numbering irregularities to know about
  • Two files share the number 0011: 0011_enable_rls.sql and 0011_nullable_inventory_prices.sql.
  • 0081 has a companion Python test, 0081_quoted_literal_substring_plant_search.test.py.
  • There are no files numbered 0085, 0086 or 0087. The app-auth changes (app_users, its triggers, must_change_password) are called "migrations 0081–0087" in docs/app/README.md and CHANGELOG.md. Those numbers clash with the files 0081–0084 in this directory, and no SQL file for app_users exists in the repository. The table is documented only in docs/supabase-schema.md.
  • 0104_job_scoped_record_names.sql (with its tests) exists but has not been applied. It would add record_name (JR-<id>:AR-<n>) to ARs and orders, plus a job_record_counters table. The app already copes with an optional record_name.
  • For some early migrations, the name in Supabase's migration history differs from the file name. NOTE.md lists the mapping, and says that 0028 and 0029 were applied but not recorded at the time.
  • A few changes have no numbered file: a temporary backup schema from before a re-ingest (dropped in 0105), and the one-time import of chat history into thread_messages.
