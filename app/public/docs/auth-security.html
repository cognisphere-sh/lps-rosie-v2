Auth, roles and security

Two kinds of people sign in to LPS. The internal team (admins) can see everything, and supplier companies (partners) can see only their own portal. A few things can also be shared through a link that works without signing in, and every link like that can be switched off with one click.

BusinessEngineersTechnical~20 min read

In short

If you read only this section, these are the main points:

  • One sign-in page for everyone. Admins and partners both sign in at /login with a username and password. Admins are the LPS team and can use the whole app. Partners are supplier companies and can use only their own company's supplier portal.
  • The app never stores passwords. Passwords are checked by Supabase Auth, a hosted sign-in service. When a password is correct, the app gives the browser its own signed session cookie, app_sid. The cookie lasts 14 days, and scripts running in the page cannot read it.
  • Admin accounts are created by hand. An operator runs a command-line script on the server. Nothing in the app can make someone an admin.
  • Supplier logins are created by an admin in the Portal access tab of the supplier's page. The app generates a password and shows it once. The supplier must choose their own password the first time they sign in, and until they do, "Choose a password" is the only page they can open.
  • A login belongs to a supplier company, not to one farm. Each login hangs off the company's head branch, and the company's portal is the head branch's portal. A login never covers another company. If a partner tries to open another supplier's portal, the app says "not found", so the partner cannot even learn whether that supplier exists.
  • Public links share one item without a login. An availability request (AR) or an order can be given a public link that contains a long random code. Anyone who has the link can see that one item, and for an AR they can also answer it. Make private stops the link working at once. Making the item public again creates a new link, so the old one stays dead. Links also stop working when the item closes.
  • Agent-published pages ("artifacts") have a Public/Private switch. A private artifact can be opened only by a signed-in admin. A public artifact can be opened by anyone with the link.
  • The browser never holds a key. The database key and the secrets the app uses to talk to the agent server stay on the server. The browser holds only its own session cookie.
Three kinds of visitor

Admins reach every page and API. Partners reach /partner/… and /api/partner/… only, and within those only their own company. Anyone, without signing in, can reach the sign-in page, a public AR or order link they hold, a public artifact, and static files such as this handbook.

Treat public links like keys

A public link works for whoever holds it. An order link shows supplier-facing order details, including customer contacts and delivery addresses. Share these links only with the intended supplier, and click Make private if a link goes somewhere it should not.

Usernames and the hidden sign-in email

Supabase Auth identifies users by email, but LPS identifies them by username. authEmail(username) in app/lib/auth.ts bridges the two:

  1. Normalise. The username is trimmed and lowercased.
  2. Email as typed. If it contains @, it is used as the Auth email unchanged.
  3. Otherwise derive one. Characters outside [a-z0-9._-] become -, leading and trailing dashes are stripped, and the result becomes <slug>@<AUTH_EMAIL_DOMAIN>.

The default domain is a reserved .invalid domain (RFC 2606), so these mailboxes do not exist. Accounts are created with email_confirm: true, so Supabase never sends mail to them. The derived email is never shown in the UI.

Do not change the email domain

AUTH_EMAIL_DOMAIN is effectively fixed once accounts exist. Changing it would orphan every account whose username is not an email address. app/scripts/create-admin.mjs repeats the same derivation, and the two copies must stay identical. Set the value in config: when it is unset, the code falls back to app.invalid but the deploy hook (scripts/app/secrets.sh) writes lps-app.invalid, so the app and the admin script could derive different emails.

Signing in, step by step

The sign-in page asks for a Username and a Password. The diagram below follows one sign-in and the request after it through the gate.

  1. Open the sign-in page. /login is public, because it is listed in PUBLIC_PREFIXES. The card is titled "Local Plant Supply", and the Sign in button shows "Signing in…" while it works.
  2. Post the credentials. The form sends POST /api/auth/login with JSON { "username": "…", "password": "…" }. A body that is not JSON gets 400 {"error":"bad request"}. Fields that are not strings are treated as empty.
  3. Find the account. verifyCredentials() returns nothing if either field is empty. It then looks up app_users by an exact match on the normalised username. It uses eq rather than ilike, because _ and % are wildcards in a LIKE pattern. If no row exists, sign-in fails. This is why no admin exists until an operator creates one.
  4. Check the password with Supabase. passwordMatches() builds a throwaway Supabase client (session persistence, token refresh and URL session detection all off) and calls signInWithPassword with the derived email. The password counts as correct only if there is no error and the returned user id equals app_users.id. The client then signs out and is discarded. The Supabase session is never used again.
  5. Answer the browser. The response is one of the following:
    StatusBodyWhen
    200{ "next": "…" }Credentials are correct. next is /change-password if a password change is owed, else /partner/<supplierId> for a partner, else /suppliers for an admin.
    401{"error":"invalid username or password"}Unknown username or wrong password. Both fail identically, so a caller cannot find out which usernames exist. The page shows "Invalid username or password."
    400{"error":"bad request"}The body is not JSON.
    502{"error":"…"}Supabase or the account table could not be reached. The page shows this as a service problem rather than a typo.
    The reply never contains the role, the supplier id or other account details beyond the next path.
  6. Set the session cookie. On success the route sets app_sid with HttpOnly, SameSite=Lax, Secure (in production), Path=/ and Max-Age=1209600 (14 days).
  7. Go to the right place. The page navigates to a safe deep link from ?next= if there is one (see deep links), otherwise to the server's next. If the server says /change-password, that always wins.

The app_sid session cookie

The session is a small signed token that the app mints and checks itself. There is no session table on the server: the signature proves the cookie is genuine, and the expiry inside it says how long it is good for.

PropertyValue
Cookie nameapp_sid (SESSION_COOKIE). Deliberately different from the harness console's pi_sid.
Lifetime14 days. Stored both in the cookie's Max-Age and as an expiry inside the signed payload.
Format<base64url(JSON payload)>.<hex HMAC-SHA256 signature>
Signing keyHMAC-SHA256 key from the server environment variable APP_SESSION_SECRET, imported with Web Crypto. It is read lazily and cached per process.
AttributesHttpOnly, SameSite=Lax, Secure in production, Path=/
RuntimeWeb Crypto and string operations only, with no server-only or node:crypto imports, so the same verification code runs in the proxy gate and in route handlers.

How a cookie is checked

resolveUser(cookieHeader) is the one function that answers "who is signed in". It takes the cookie named exactly app_sid (names such as x_app_sid or pi_sid do not match), URI-decodes it and passes it to readSession(). That function fails closed. It returns "nobody" when any of these is true:

  • the token has no ., or either part is empty;
  • the signature is not even-length lowercase hex;
  • signature verification fails or throws (Web Crypto verification is constant-time);
  • the payload is not valid base64url JSON;
  • the expiry is missing or already past;
  • the role is not admin or partner, or the id or username is not a string;
  • the role and scope do not match: a partner with no supplier id, or an admin with one;
  • the signing secret is not configured.

The resulting SessionUser is { id, username, role, supplierId, mustChangePassword }.

Signing out

Sign out clears the cookie in that browser. Because sessions are signed rather than stored, and neither the gate nor the per-route checks look the account up again once a cookie is minted, a cookie stays valid until it expires even if its account is later reset or deleted. Rotating APP_SESSION_SECRET on the server is the way to sign everyone out at once. The deploy script generates this secret once and reuses it on every restart, so a normal restart keeps people signed in.

Forced password change

A supplier login starts on a password the app generated and an admin passed on, perhaps by phone or message. Until the supplier replaces it, the gate treats that password as not yet private: the session can reach only the "Choose a password" page.

  1. The flag is set. app_users.must_change_password becomes true when an admin creates a partner login or resets its password. The admin script does not set it, because the operator typed that password. A reset changes the database only: a session already open keeps its old cookie (without the flag) until that browser signs in again.
  2. The flag travels in the cookie. At sign-in it is copied into the session as p: true. The gate reads only the cookie, never the database.
  3. Everything else is closed. While the flag is set, any page other than /change-password redirects there, and any /api call gets 403 {"error":"password change required"}. /api/auth/* stays open, which is what lets the form save and lets Sign out work.
  4. The user chooses a password. The page is titled "Choose a password" and explains: "You signed in with a password we generated for you. Replace it with one only you know to carry on." The button is Save and continue.
  5. The cookie is re-minted. On success the server sets a fresh app_sid without the flag and returns where to go next (/partner/<id> or /suppliers). Without this step the old cookie would keep sending the user back to the form.

The password form

The same form (ChangePasswordForm) appears on /change-password and on the portal's Settings page (/partner/:id/settings). It has Current password, New password ("At least 10 characters. Pick something only you know.") and Confirm new password ("The two do not match." on a mismatch). The button is enabled only when all three are valid. Success shows "Password changed." Admins have no link to this form, but they can open /change-password directly.

Creating and managing logins

Partner logins: the Portal access tab

Supplier logins are managed in one place only: the Portal access tab on a supplier's page (/suppliers/<id>?tab=access). The tab explains: "One set of logins per company, shared across its farms."

  1. Add an account. Type a username in Add an account (it is pre-filled with the first contact email found across the company's locations; "What they type to sign in. An email is fine; it is never written to.") and click Create login.
  2. Save the password now. A box shows "Save these now — the password cannot be shown again" with the Portal address, Username and Password. Copy message copies a ready-to-send hand-over text, and Copy link copies the portal URL (<origin>/partner/<head branch id>).
  3. Send it to the supplier. They sign in and must choose their own password straight away.
  4. Reset or delete later. Each account row has Reset password (shows a fresh one-time password and forces another change at the next sign-in) and a delete button, which asks for confirmation first. Neither ends a session that is already signed in (see the session cookie), although the delete confirmation says the person loses access immediately. One exception: deleting a company's last login clears its LPS Partner flag, and most portal routes then answer 404 for that company (see the second layer).
"LPS Partner" follows the logins

A supplier is marked LPS Partner exactly while its company has at least one portal login. The flag is kept on the head branch row only. Adding the first login turns it on, and deleting the last one turns it off. Nobody edits this field by hand; a database trigger keeps it in step. Partners receive availability requests in their portal. Suppliers that are not partners get a public link on each AR instead, for email outreach.

The admin API

Every handler on /api/suppliers/:id/partner-account checks for an admin session itself, even though the gate already keeps partners out, because what this route hands out is other people's credentials. A non-admin gets 403 {"error":"forbidden"}.

MethodBodyResult
GETnone{ accounts: [{ id, username, createdAt }], scopeId }, oldest first, no-store. Lists partner rows whose supplier_id is the company's head branch.

What happens inside a create, reset and delete

Create (createPartnerAccount):

  1. Normalises the username. It is required and at most 120 characters.
  2. Resolves the company with partnerScopeId(); an unknown or inactive supplier fails with "supplier not found".
  3. Refuses a username that already exists anywhere ("the username … is already taken"), because usernames are global.
  4. Generates a password with generatePassword(): 16 characters from abcdefghjkmnpqrstuvwxyz23456789 (no 0, o, 1, l or i, so it can be read aloud), drawn from node:crypto random bytes and grouped xxxx-xxxx-xxxx-xxxx. That is just under 80 bits (the source comment says about 78).
  5. Creates the Supabase Auth user with the derived email and email_confirm: true.
  6. Inserts app_users { id, username, role: 'partner', supplier_id: <head branch>, must_change_password: true }. If that insert fails, the Auth user is deleted again so nothing is left half-made.
  7. Leaves suppliers.is_lps_partner to the database trigger.

Reset and delete look the account up by its id and the company's head branch and role = 'partner'. One supplier's page therefore cannot reset or delete another company's login.

is_lps_partner is excluded from the writable supplier fields in app/lib/queries.ts and shown read-only on the profile grid. A test asserts both.

Admin logins: app/scripts/create-admin.mjs

Admins are created or reset from the server's command line. There is no sign-up and no seed admin from configuration; an older seed was removed on 2026-08-30, and a test asserts it stays gone.

cd app && set -a && source ../config && set +a && node scripts/create-admin.mjs <username> '<password>'
  • It needs SUPABASE_URL and SUPABASE_SECRET_KEY (and optionally AUTH_EMAIL_DOMAIN) in the environment, and exits with code 2 if they are missing.
  • If the username belongs to a partner, it refuses and says to reset it from the supplier page, so partner resets stay scoped to their company.
  • If the username is an existing admin, it resets the password. Otherwise it creates the Auth user and an app_users row with role: 'admin' and supplier_id: null.
  • It then verifies the sign-in on a separate client and prints { username, authEmail, role, userId, action, signInVerified }. It never prints the password.
  • The password is passed on the command line so it never lands in a file, but it will appear in shell history; clear it if that matters on the server.

The proxy gate

app/proxy.ts is the app-wide gate. It is the Next.js 16 "proxy" file (the replacement for middleware.ts) and runs before every request it matches. It looks only at the path and the app_sid cookie; it never queries the database.

The constants

NameValueMeaning
PUBLIC_PREFIXES['/login', '/api/auth']Open to everyone. A path matches a prefix when it equals it or starts with the prefix plus /.
PUBLIC_AVAILABILITY/^\/(?:api\/)?public\/(?:availability|orders)\/[0-9a-f-]{36}$/iOpen to everyone. Despite its name, it covers both AR and order links, both the pages (/public/…) and their APIs (/api/public/…), for every HTTP method. The handlers then require a canonical UUID.
PUBLIC_ARTIFACT/^\/a\/[a-z0-9][a-z0-9-]*\/public\/artifacts\/[a-z0-9][a-z0-9-]*$/Open to everyone. Only the /public/ shape; the sibling /a/<agent>/private/… stays gated.
CHANGE_PASSWORD'/change-password'The only page an account that owes a password change may reach.
PARTNER_PREFIXES['/partner', '/api/partner']Where a partner belongs, and the only area a partner may reach.

Decision order

  1. Public? A path under PUBLIC_PREFIXES, or matching PUBLIC_ARTIFACT or PUBLIC_AVAILABILITY, passes with no session check.
  2. Who is it? The gate reads app_sid with resolveUser().
  3. Nobody. An /api… path gets 401 {"error":"unauthorized"} as JSON (never a redirect, so a fetch() gets an error it can handle rather than the login page). Any other path gets a 307 redirect to /login?next=…, carrying a sanitised return path and no other query values.
  4. Password change owed. If the session has the flag and the path is not /change-password: /api… gets 403 {"error":"password change required"}, and pages redirect to /change-password with the query removed.
  5. Partner outside the portal. If the role is partner and the path is neither /change-password nor under PARTNER_PREFIXES: /api… gets 403 {"error":"forbidden"}, and pages redirect to /partner/<supplierId>. /change-password is exempt so the two checks cannot bounce a partner back and forth.
  6. Otherwise, pass. Admins reach everything.

What the gate does not run on

The gate's matcher skips Next.js internals (_next/static, _next/image, favicon.ico) and any path whose last segment has a file extension. This is required for installing the app as a phone app (PWA): /manifest.json, /sw.js and the icons must load for a signed-out browser, because Chrome's install check does not follow redirects. It is also why this handbook, served from /docs/*.html, is public. Only the .html paths are: the bare /docs or /docs/ has no extension, so the gate redirects a signed-out reader to /login, and no Next.js page exists there for a signed-in one. The entry URL is /docs/index.html.

What the gate deliberately leaves to others

The gate can tell that a partner is inside /partner, but not whether the supplier id in the URL belongs to that partner's company; only the database knows which branches belong to which company. That check is done by canAccessSupplier() in every /api/partner/:id route (see company scoping). In the words of the source comment: the gate "keeps suppliers out of the internal app", and the per-route check "keeps them out of each other's portals". Both are needed.

Deep links through sign-in

When a signed-out person opens a link, the gate remembers where they were going in ?next=, but only in a safe, minimal form.

  • jobLoginReturn(pathname, searchParams) keeps only the path. The one exception is /jobs, which keeps ?jr=<id> when there is exactly one jr value and it is a positive whole number. The source rule: "Never put unrelated query values (including credentials) in the login URL." For example, /jobs?jr=71&token=… becomes /login?next=/jobs?jr=71.
  • loginDestination(next, fallback) checks the untrusted next on the sign-in page. It ignores it and uses the server's fallback when the fallback is /change-password; when next is missing, does not start with /, or starts with //; when it contains a backslash or control characters; when it would change origin or carries a # fragment; when the path contains encoded /, \ or control characters; or when it points under /login or /api. When it does accept next, it keeps only the path (plus a valid jr on /jobs) and drops every other query value. This prevents the sign-in page being used to bounce people to another site.
  • The password-change redirect and the partner redirect both take precedence over a remembered job link.

Related routing rules

  • /portal/:path* permanently redirects to /partner/:path*, because the portal lived at /portal until 2026-08-26.
  • The only rewrite to the harness is /api/gws/oauth/callback, the Google sign-in return for an agent. The harness validates it with a single-use state value issued when the flow started. It is not on the gate's public list, so the admin's own signed-in browser completes it.

Company-scoped supplier access

A supplier company can have several branches (farms, yards). Each suppliers row has a head_branch_id; a single-site supplier points at itself, and the value is never null and never chains. A partner login hangs off the company's head branch. canAccessSupplier admits any active branch of that company and nothing else, but the LPS Partner flag lives on the head branch alone (see the second layer below), so in practice a company's portal is /partner/<head branch id>. See Suppliers, plants and catalogue for how branches are modelled.

The three functions

FunctionAnswersRule
partnerScopeId(supplierId)Which company is this supplier?Reads id, head_branch_id for an active supplier and returns head_branch_id ?? id. Unknown or inactive suppliers return null.
canAccessSupplier(user, supplierId)May this session see this supplier?Admin: yes. Partner with no supplier id: no. Partner whose head branch is this id: yes. Otherwise yes only if partnerScopeId(supplierId) equals the partner's head branch.

Why "not found" and not "forbidden"

Answering 403 would confirm to one partner that another supplier id exists. Answering 404 reveals nothing.

The second layer: partnerSupplier

Most portal routes also call partnerSupplier(id), which returns the supplier only if that exact row is active and marked LPS Partner, and the route answers 404 otherwise. Because only the head branch carries the flag, these routes answer 404 for a farm (non-head) id. Row reads then filter on the exact supplier id (availability_requests.supplier_id or orders.supplier_id), so a request or order belonging to another supplier returns 404 even inside the right company's portal. The live-update stream (/events) and the two chat routes rely on requirePartnerAccess alone; the update stream carries data-free "something changed" signals only, and the chat routes require the supplier to be an active partner with a chat thread.

The /partner/[id]/* pages are client components that load everything through these gated APIs, so scoping happens at the API, not in the page. The full list of portal endpoints is in the API reference.

History

The portal was public until 2026-08-30, and the id in the URL was the only scoping. Since then it requires a partner (or admin) session and the company check above.

A public link lets someone without a login see one item. It is used mainly for suppliers who are not LPS Partners, who receive their availability requests by email. Sharing and revoking

  1. Make public. The Share button on an AR (or Share public link on an order) opens a panel with Make public. The server writes a fresh randomUUID() into public_token. A draft AR is refused ("Publish this draft before sharing it"), as is a closed AR, and so is a closed order ("This order is closed"). Clicking Make public always writes a new UUID.
  2. Copy the link. Copy public URL (AR) or Copy public link (order) copies <origin>/public/…/<uuid>.
  3. Make private. The server sets public_token to null. The panel confirms "Request is private. Previous link revoked." (or "Order is private. Previous link revoked."). The old link answers "This link is no longer available" from that moment.
  4. Make public again. A new UUID is issued. The old link never comes back.

The share panels state the rule in plain words. For an AR: "Anyone with this link can view and answer this request until it closes or is made private." For an order: "Anyone with this link can view supplier-facing order details, including customer contacts and delivery addresses, until it closes or is made private."

What a public order link shows

An order link shows the supplier view of the order: line items, prices and statuses, schedules, and the linked jobs' customer name, company, email, phone and delivery address. An AR link shows customer and shipping details only when the AR is set to share customer details and is linked to exactly one job. Neither shows the internal notes for the customer, quantity allocations or portal navigation.

How a token is checked

  • The gate's pattern admits any 36 hex-or-dash characters; the handler then requires a canonical UUID, /^[0-9a-f]{8}-(?:[0-9a-f]{4}-){3}[0-9a-f]{12}$/i, and returns "not found" for anything else.
  • The row must have that token and an open status (an AR not closed or draft; an order active and not closed_won or closed_lost), and its supplier must be active.
  • The data is loaded in the supplier view, the same reduced view a partner sees. The public payload never includes the token itself.
  • Both lookups re-check the token after loading the data (the order lookup runs its token query a second time), so a revoke that happens during the request is honoured.
  • Every write through an AR link re-resolves the token inside the database function (answer_public_availability, submit_public_availability_note), which only the server's service role can call.
  • Responses carry Cache-Control: no-store and Referrer-Policy: no-referrer; AR responses also send X-Robots-Tag: noindex, nofollow. The pages set robots: noindex, nofollow and referrer: no-referrer, so the link is not leaked to other sites or search engines.

Agent artifacts: public and private

Agents can publish HTML pages, such as reports, called artifacts. Each artifact has two addresses, and a Public/Private switch decides which one works. No token is involved: the flag kept by the harness's artifacts plugin is the whole rule.

RouteWhoBehaviour
GET /a/<agent>/public/artifacts/<slug>anyoneExempt from the gate (PUBLIC_ARTIFACT). A plain pass-through with no secret attached; the plugin serves the page only while it is flagged public, and answers 404 otherwise.
GET /a/<agent>/private/artifacts/<slug>adminBehind the gate, so partners are redirected to their portal and signed-out visitors to sign-in. Loads the artifact's details server-side and shows the share switch above an iframe of …/raw.
GET …/private/artifacts/<slug>/rawadmin (checked in the route)Returns the private HTML. A non-admin gets 401 sign in.
POST …/private/artifacts/<slug>/shareadmin (checked in the route)Body { "public": true|false }. Anything other than literal true makes it private.
  • Inputs are checked before the harness is called. The agent must be listed in ARTIFACTS_AGENTS (a comma-separated allowlist) and the slug must match ^[a-z0-9][a-z0-9-]{0,63}$. Anything else is a 404 that never reaches the harness. On raw and share the admin check runs before this input check.
  • The switch. The Public/Private button sits above the iframe. Its tooltip reads "Anyone with the link can read this. Click to make it private." or "Only signed-in users can read this. Click to publish it." In practice "signed-in users" means signed-in admins. A read-only "Link to share" field shows the public address.
  • Sandboxed. Agent HTML is served with Content-Security-Policy: sandbox (without allow-same-origin), so it runs in an opaque origin and cannot read the app's cookies or storage. That is also why the switch sits outside the iframe. The app passes through only content-type, content-security-policy, referrer-policy, x-content-type-options and cache-control from the harness.
  • Server-side secret. The private, raw and share calls attach x-artifacts-secret from ARTIFACTS_APP_SECRET on the server. The browser never sees it.

App to harness: the bearer and its allowlist

App users are not harness users. When the app needs the agent harness (to chat with an agent, or to change agent settings), it authenticates as itself and names the acting user in a header. harnessAuthHeaders(username) in app/lib/harness.ts builds:

Authorization: Bearer $HARNESS_APP_SECRET
X-App-User:    <username>

The harness trusts X-App-User only together with a valid bearer. The bearer carries full operator access to the harness, so the app never exposes it as a general proxy. Only two routes use it.

/api/harness/*: the settings gateway

This route's allowlist of method-and-path pairs is, in the source's words, the whole security boundary. A pair that is not listed gets 404 {"error":"not found"}. A listed pair then requires an admin session (403 {"error":"forbidden"} otherwise), checked in the route itself. If the harness cannot be reached the answer is 502 {"error":"harness unreachable"}.

<agent> must be a known agent id (daisy, rosie, nova, lily). Everything else, including other file paths, other providers and unknown agents, is refused. The file endpoint is pinned because, unpinned, it could read and write anywhere under an agent's directory.

  • The agent must be a chat agent (daisy, rosie, nova) and the action one of messages, send, upload, file, reset, threads, read; anything else is a 404.
  • Forwards to the harness webchat plugin with the bearer and X-App-User. Details are in Chat and live updates.

Server-only secrets

All database access and every harness call happen on the app server. This section names the variables involved; their values are never written into documentation, code or the browser.

  • Where they come from. app/.env.local is generated by scripts/server.sh from the repository's config file, with scripts/app/secrets.sh adding to it. It is gitignored and must not be edited by hand. See Deployment and operations.
  • Also in the file. scripts/server.sh also writes APP_USER, APP_PASS and PORT. APP_USER and APP_PASS are the harness console's operator login; the app's code does not read them, and they are not an app sign-in.
  • No public variables. There is no NEXT_PUBLIC_* variable anywhere in the app, and the browser is given no Supabase key of any kind. Row-level security is enabled on every table; the app's server uses the service-role key, which bypasses it.
  • Build-time guard. The modules that hold or use secrets (lib/supabase.ts, lib/auth.ts, lib/partner-auth.ts, lib/harness.ts and others) import server-only. Importing one from a browser component is a build error.
  • Never sign in on the shared client. supabase-js keeps a signed-in session in memory even with persistence off, which would make later queries run as an ordinary user instead of the service role, and row-level security would then refuse them. Password checks therefore use a throwaway client. A test reads the source of the auth modules and fails if any sign-in call appears on the shared client, or if there is more than one signInWithPassword in lib/auth.ts.
  • Storage. Plant photos live in a private bucket. GET /api/photos/:id/image (admin, behind the gate) looks up the photo's storage path from its row and hands out a signed URL that lasts one hour, so the browser never names a storage path. Inventory source files in the lps bucket are handed out by GET /api/file?path=… (admin, behind the gate): the path must match a recorded inventory_sources.file_path (an unknown path gets 404), and the app redirects to a one-hour signed URL, so the route cannot be used to sign arbitrary objects.

  • Its own app_sid cookie, which scripts cannot read
  • The /api/auth/me answer (username, role, supplier id)
  • A generated partner password, shown once to the admin who created it
  • Public tokens of ARs and orders the user is allowed to see
  • Any of the secrets in the table above
  • Any Supabase session token: the Supabase session is discarded right after the password check

Threat notes

The main risks this design addresses, and how it addresses each one.

RiskWhat the design does
Finding out which usernames existUnknown username and wrong password give the same 401 and the same message.
One supplier seeing another's dataPath-level gate keeps partners in the portal; canAccessSupplier scopes them to their company; row reads filter on the exact supplier id; refusals are 404 so other suppliers' ids are not confirmed.
A forged or tampered sessionHMAC-SHA256 signature over the whole payload, constant-time verification, expiry inside the signed payload, and a role/scope consistency check. Anything unexpected reads as "signed out".
A session outliving its accountSessions are stateless, so resetting or deleting a login does not end a session already open. It lasts until its 14-day expiry. Rotating APP_SESSION_SECRET ends every session at once.
Session theft by page scriptsHttpOnly cookie; agent artifacts run in a sandboxed, opaque origin; no keys or Supabase tokens in the browser.
Cross-site requestsSameSite=Lax cookie, so it is not sent on cross-site background requests.
A generated password being known to othersShown once; the account can reach only "Choose a password" until it is replaced.
Open redirect or leaking data through the sign-in URLjobLoginReturn keeps only the path (and a valid job id); loginDestination rejects anything that leaves the site or targets /login or /api.
Guessing a public linkLinks carry a random UUID (randomUUID() in the app, gen_random_uuid() when the database issues one at send); malformed tokens are rejected before any lookup.
A public link being leakedOne-click revoke takes effect immediately; re-publishing issues a new UUID; links clear automatically when the item closes; responses are not cached, not indexed and send no referrer. The share panels warn what each link shows.
The browser reaching the harnessThe operator bearer stays on the server behind an explicit allowlist with an admin check; portal and notification calls use narrow single-purpose secrets.
Database key exposureService-role key only in server-only modules; no NEXT_PUBLIC_* variables and no Supabase key in the browser; row-level security enabled on every table.
Accidental escalation to adminAdmins are created only from the server's command line; the script refuses to turn a partner login into an admin.
Operator guidance

To sign every user out at once, rotate APP_SESSION_SECRET and restart the app. If a public link was sent to the wrong person, make the item private and, if still needed, public again to get a new link. If a partner password may be known to someone else, use Reset password on the Portal access tab. A reset stops the old password working but does not end sessions already signed in with it; to cut those off as well, also rotate APP_SESSION_SECRET and restart, which signs everyone out.

Reporting a security concern

This handbook is public. If you find a weakness, report it privately to the LPS system owners rather than writing it into these pages or a shared channel.
