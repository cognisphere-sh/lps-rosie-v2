Architecture

LPS is one web app and one AI-agent server, running on a single Linux machine, with all business data in a hosted Supabase database. People use the web app in a browser. The AI agents (Rosie, Daisy, Nova and Lily) work inside the agent server. They talk to people only through plugins.

EngineersTechnical~18 min read

In short

If you read only this section, these are the main points:

  • Two programs, one server. The web app (built with Next.js) is what the LPS team and supplier partners open in a browser or install as a phone app. The harness (the Cognisphere agent server) runs the four AI agents and has its own operator console. Both run as background services, and both restart automatically.
  • One front door. The internet talks only to nginx, which handles HTTPS. The harness listens only on the server itself. The provisioning firewall (an AWS security group, or ufw on Contabo) opens only HTTP, HTTPS and SSH, so the app's own port is not reachable from outside either.
  • One source of truth for business data. Suppliers, plants, customers, jobs, availability requests, orders, user accounts and chat transcripts all live in Supabase, a hosted PostgreSQL database with sign-in and file storage. The app and the agents both read and write the same database.
  • The browser never holds a key. All database access, and every call to the agent server, happens on the app's server. The browser holds only its own sign-in cookie.
  • Screens update themselves. When anyone changes something (a staff member, a supplier, or an agent), the database tells the app server, and the app server sends a short "something changed" signal to every open screen. Each screen then reloads what it shows.
  • Agents talk to people through plugins. Chat, Telegram, Gmail, timers, publishing pages and agent-to-agent messages each go through a plugin. Agents also have shell tools that reach the network directly: SQL and file storage for Rosie and Daisy, plus web search and a headless browser for all four. Their system prompts require a person's explicit yes before an agent emails a customer or supplier. That rule lives in the prompt, not in code.
Who uses what

Admins (the internal LPS team) can use the whole app and chat with the agents. Partners (supplier companies) can see only their own company's supplier portal. Anyone with a public link can open one shared availability request or order, or one agent page that has been made public, without signing in. This handbook is public too.

nginx

nginx is the only process that faces the internet. scripts/setup-server.sh writes two server blocks. $DOMAIN proxies to the app, and $CONSOLE_DOMAIN proxies to the harness console. Each block forwards Host, X-Real-IP, X-Forwarded-For, X-Forwarded-Proto and the Upgrade/Connection headers (for WebSocket upgrades). The app's SSE responses send X-Accel-Buffering: no, so nginx does not buffer them. certbot adds HTTPS and redirects plain HTTP. A deployment hook (scripts/app/configure-nginx-upload-limit.py) raises client_max_body_size to 25 MB for exactly two app paths: the internal chat upload route and the partner chat route. Every other path keeps nginx's default body limit.

Next.js app

The app serves both audiences from one codebase. The admin workspace (Suppliers, Plant search, Photos, Customers, Jobs, Agents, Settings) mounts the Shell chrome. The supplier portal under /partner/<id> mounts PartnerFrame. Both are built on one shared WorkspaceFrame. There are 23 pages. Nearly all of them are client components that draw at once and then fetch the app's own /api/* routes. No page reads Supabase while it is being built on the server. The one server-side data fetch in a page is the private artifact page, which asks the harness for an artifact's metadata. The app is also an installable PWA (public/manifest.json, public/sw.js). Its service worker caches only page navigations, network first, and never caches API calls. See Frontend: routes and components.

Proxy gate

app/proxy.ts runs before every request that its matcher covers. It decides in this order:

  1. Public paths pass. /login, /api/auth/*, public AR and order token links (/public/availability/<uuid>, /public/orders/<uuid> and their /api/public/… twins), and public artifacts (/a/<agent>/public/artifacts/<slug>).
  2. No valid session. /api/* gets 401 {"error":"unauthorized"}, never a redirect. A page gets a redirect to /login?next=….
  3. Password change owed. Every gated path except /change-password is refused: the API gets 403 and a page gets a redirect. (/api/auth/* is already public, so the form can still post the change and sign out.)
  4. Partner outside the portal. A partner session anywhere other than /partner, /api/partner or /change-password gets 403 (API) or a redirect to their own portal.
  5. Everything else passes. Admins reach everything.

The gate sees only a path and a cookie, never the database. It can keep suppliers out of the internal app, but it cannot tell which company a supplier id belongs to. Company scoping is therefore done per request by requirePartnerAccess() / canAccessSupplier() in every /api/partner/:id/* route. The matcher skips Next internals and any path ending in a file extension. That rule keeps the PWA manifest, service worker and icons readable by a signed-out browser, and it is also why this static handbook (/docs/*.html) is public. See Auth, roles and security and the auth gate sequence ↗.

Route handlers and the server library

Route handlers are thin. They parse and validate input, then call a domain module in app/lib/, for example availability-queries.ts, order-queries.ts, job-request-queries.ts, queries.ts or auth.ts. The domain module talks to Supabase through the one shared server client in lib/supabase.ts. Multi-step business transitions are Postgres RPCs, such as send_availability_request, create_order, confirm_order and delete_job_request. That way the rules hold no matter who writes, the app or an agent. Generic single-cell edits go through PATCH /api/rows against a per-table list of writable columns. A few handlers re-check the admin role themselves rather than relying on the gate alone, mostly the ones that hand out operator access or credentials: /api/harness/*, /api/chat/<agent>/<action>, /api/orders/*, /api/suppliers/:id/partner-account, and the artifact raw/share routes. The full list is in the API reference.

Inside the harness

The harness runs the agents and their plugins. Messages from people arrive through plugins, and replies leave through them. For each batch of incoming messages on a thread, the harness spawns a fresh LLM child process: the pi coding agent (pi --mode rpc), pinned to 0.84.4 by each agent's bootstrap/bootstrap.sh. The process reads the assembled system prompt and the thread's history, then works using its skills and shell tools. Those shell tools can reach the network directly (for example psql to Supabase, Storage uploads, web search, a headless browser), so plugins are the channel to people, not a network sandbox. Everything an agent writes in its turn is internal. Nothing reaches a person until a plugin CLI runs, such as webchat-cli send, telegram-cli send-message or gws gmail +send.

Threads

A thread is one conversation and routing identity. All of an agent's threads share one workspace, knowledge base and skill set, and each thread has its own queue and session. The threadIdStrategy setting maps incoming messages to threads. Plugins can override it per message with threadIdOverride, which is how the app pins a chat message to jr-<id>, supplier-<slug>, customer-<slug> or main. The panel's main conversation and Telegram's main route are the same thread. Agents can also start fresh-context task threads by messaging themselves on <ThreadId>-§-[TASK]-§-<slug>.

The harness library is a dependency, not a fork

The harness is the installed package @cognisphere-sh/cognisphere-harness, pinned to 0.12.0 in harness/package.json. Nobody edits it in place. Changes that need new harness capability go upstream, and version bumps go through the cognisphere-upgrade skill. Local behaviour belongs in user-space plugins, agent directories and the scripts/app/ hooks.

Request paths

These are the main paths a request can take through the system. Every browser request first passes nginx, then (for gated paths) the proxy gate.

1. Admin reads a page

  1. Browser → nginx → app. For example, GET /suppliers. The gate verifies app_sid and confirms the admin role.
  2. Page shell renders as a client component, then fetches, for example, GET /api/suppliers?q=&page=… (debounced 300 ms).
  3. Route handler → lib/* → Supabase with the server-only service_role client. JSON comes back to the browser.

2. A write, and how open screens learn about it

  1. The write lands in Postgres. It may come from an admin (PATCH /api/rows, an RPC route), a partner (/api/partner/:id/*), a public link holder, or an agent's SQL.
  2. Supabase Realtime delivers a postgres_changes event to the app server's single channel, lps-workspace. That channel watches threads plus the job-workflow tables (job_requests, job_request_items, availability_requests, candidates, orders, order_items, order_item_job_request_items, customers, suppliers).
  3. The relay fans out over SSE. A job-table change sends {"type":"jobs"}, which carries no data, to /api/chat/events (the team) and /api/partner/:id/events (a portal). A threads change sends the team stream a thread event with the thread's summary (newest-message preview, sender, read cursors, working flag). The portal's chat stream, /api/partner/:id/chat/events, gets only a content-free {"type":"ping"} when that supplier's Rosie thread moves.
  4. Each screen re-reads its own scoped API after a 200 ms batch. Pages also re-read on a 60 s fallback poll, on focus, on tab return, on stream reconnect and on online.

See Chat and live updates and the live-updates data flow ↗.

3. Team chat with an agent

  1. Browser → POST /api/chat/<agent>/send with {text, attachments, threadId, page}.
  2. The chat proxy (app/app/api/chat/[...path]/route.ts) checks for the admin role before anything else. It validates the agent against CHAT_AGENTS and the action against an allowlist, validates the canonical thread id, and queues the request per (agent, thread). It then forwards to /webhook/<agent>/webchat/api/send with the app bearer and X-App-User.
  3. The webchat plugin inserts a thread_messages row (a failed insert fails the send) and calls ctx.notify("web_message") on that thread. The agent wakes.
  4. The agent replies with webchat-cli send, which posts to api/reply with the in-harness webhook secret. The reply is recorded as another row.
  5. The row insert updates threads, and Realtime and the SSE relay emit a thread event carrying the thread summary and a short preview. The open panel pulls GET …/messages?since=… for the full messages. Full message bodies and attachments are never pushed over SSE.

See the chat message sequence ↗.

4. Supplier portal

  1. Partner browser → /partner/<id>/…. The gate allows it because the path is under the portal.
  2. /api/partner/:id/* runs requirePartnerAccess(), which resolves the head branch and returns 404 (not 403) for another company. Most routes then run partnerSupplier(), which requires an active LPS Partner.
  3. Submitting answers or changing an order commits in Postgres first. The route then calls notifySupplierEvent() → POST /webhook/rosie/supplier-events/notify with X-App-Secret, which wakes Rosie on the supplier's thread. This is best-effort, with a 5 s timeout and no retry. The data is already saved. Public-link answers and admin AR edits use the same notifier.
  4. Portal chat goes server to server: /api/partner/:id/chat → webchat api/app-* with X-App-Secret. The supplier sees only portal-flagged messages.

See Supplier portal and public links, the AR round-trip sequence ↗ and the supplier-events data flow ↗.

5. Public token links

/public/availability/<token> and /public/orders/<token> skip the gate. The handler checks that the token is a strict UUID, then looks up the record by public_token. The record must still be open, and its supplier must be active. Responses are no-store and no-referrer, and they are not indexed. An AR link holder can answer and submit through service-role-only RPCs that re-resolve the token inside SQL on every write.

6. Settings and the harness admin API

The Settings page calls /api/harness/*. That route allows a fixed set of method and path pairs: the harness timezone, the model provider and OAuth flow, reading an agent and writing its config, Google sign-in status, start and stop, and one pinned scheduler file per agent. Anything else returns 404. The route then requires the admin role and forwards with the bearer. Google's OAuth browser redirect is the only exception. /api/gws/oauth/callback is rewritten by next.config.ts straight to the harness, which authenticates it with its single-use state nonce.

7. Agent work

  • Database: Rosie and Daisy run scripts/agent/supabase/query, a wrapper around psql through the Supabase pooler. Its lexical guard allows SELECT, INSERT, UPDATE and function creation, and blocks DELETE, DROP, ALTER, TRUNCATE, GRANT and similar statements. Their writes trigger the same Realtime fan-out as the app's.
  • Email in: gws polls Gmail, emits email_received with a preview, and the agent reads the full mail on demand.
  • Artifacts out: artifact publish stores HTML in plugin state. The app serves it at /a/<agent>/{public,private}/artifacts/<slug> under a CSP sandbox. Private pages require an admin.
  • Handoffs: scripts/agent-msg/send --to-agent … --thread-id …. For example, Daisy forwards order email to Rosie, and any agent sends code requests to Nova.

The harness exports every key in an agent's secret buckets (its own and its plugins') into that agent's environment. For example, the webchat plugin's Supabase key is visible to the shell of every agent that carries webchat, Nova included.

Two halves of partner scoping

The gate keeps partners inside /partner. canAccessSupplier() keeps each company out of the others' portals. Every new /api/partner/:id/* route must call requirePartnerAccess(), because the gate alone cannot tell companies apart.

What the browser holds, and what it never holds

Holds: its own app_sid cookie, which JavaScript cannot read. It also holds the /api/auth/me answer (username, role, supplier id), public tokens of records the user may share, and a generated partner password, shown once in the admin's Portal access panel.

Never holds: SUPABASE_SECRET_KEY, APP_SESSION_SECRET, HARNESS_APP_SECRET, ARTIFACTS_APP_SECRET, WEBCHAT_APP_SECRET, SUPPLIER_EVENTS_APP_SECRET, any Supabase JWT, or a user's derived Supabase Auth email. There is no NEXT_PUBLIC_* variable anywhere in the app. Importing lib/supabase.ts, lib/auth.ts or lib/harness.ts from client code is a build error, because they import server-only.

Two kinds of "conversation"

The chat transcript people see is a set of rows in Supabase, written only by the webchat plugin. The agent's own memory of that conversation is its harness session. "Clear conversation" resets both: it deletes the thread's message rows and resets the harness thread context. A deleted job's chat is tombstoned in deleted_job_threads, and Rosie's webchat plugin purges that thread's session on its next sweep (every 15 seconds, and before each request), retrying if a turn is in flight.

Read state and the "working…" indicator

"Read" is server state, not browser state. A thread is unread for the team when threads.last_seq > threads.web_read_id. The web cursor moves when the open panel polls with read=1, when you send, and when you use Mark all read. The portal cursor moves only on portal reads and sends. An agent reply moves neither cursor, because the reply is exactly what the unread dot exists to announce. "Agent is working" is threads.pending_since (shown for at most pendingTimeoutSec, default 900 s) or an in-flight event in the harness queue. The plugin clears it on restart and when the agent replies.

Key design decisions

Same-origin harness proxy

Decision: the browser never calls the harness. Everything it needs from the harness goes through app routes on the same origin: /api/harness/* (an allowlist), /api/chat/<agent>/<action> (an action allowlist plus a per-thread queue), the artifact routes, and the partner chat route.

Why: the harness sends no CORS headers, so a cross-origin call from the browser would fail anyway. More importantly, the app authenticates to the harness with a bearer that carries full operator access. Exposing that to the browser, or forwarding arbitrary paths, would hand any signed-in user the whole harness, including agents' prompts, files and secrets paths. A server-side pass-through lets the app attach the bearer itself, allow only the endpoints a screen needs, pin the one file the scheduler table edits, and require the admin role. The single exception, the Google OAuth callback rewrite, exists because a browser redirect cannot carry a bearer. The harness authenticates that one route with a single-use nonce instead.

Harness on localhost

Decision: the harness binds to 127.0.0.1, and the app reaches it at HARNESS_URL (default http://127.0.0.1:3142). nginx is the only public entry, with the provisioning firewall closing every other port. The operator console is exposed separately at $CONSOLE_DOMAIN, behind its own login.

Why: the harness's webhook router does not authenticate. Each plugin checks its own callers. Keeping the port on loopback means the shared secrets above are a second line of defence, not the only one. Loopback calls are also fast and need no TLS, and both services can be restarted independently. server.sh restart app leaves the agents running, which matters because Nova deploys the app from inside the harness.

App-owned sessions

Decision: since 2026-08-30 the app runs its own sign-in. Supabase Auth checks the password on a throwaway client. The app then mints its own signed app_sid cookie and discards the Supabase session. App users are not harness users. The app calls the harness as itself (bearer plus X-App-User).

Why:

  • Two audiences. Supplier partners needed real logins scoped to their company, which the harness console's user model could not express.
  • A self-contained check. The cookie's payload (user id, role, head-branch supplier id, expiry, password-change flag) is HMAC-signed and verified with Web Crypto alone. The gate can therefore decide every request without a database or network call.
  • No Supabase JWT in the browser. Discarding the Supabase session keeps one out. Signing in on a throwaway client also keeps the shared server client on service_role. A sign-in on the shared client once made later queries run as authenticated, which RLS refused. lib/auth-client-isolation.test.ts now guards against that.
  • Deliberate admin creation. Admin accounts are created only by an operator script (app/scripts/create-admin.mjs), which also resets an admin's password. Nothing in configuration bootstraps an admin.

Server-only Supabase

Decision: exactly one Supabase client exists in the app (lib/supabase.ts). It is server-only and holds the secret key. There is no anon key, no browser Supabase client, and no NEXT_PUBLIC_* variable. Browsers get live updates from an SSE relay that the app server feeds from one Realtime channel.

Why:

  • No browser path to the database. RLS is on for every table and anon reaches no table, so a browser key would have nothing it could safely read.
  • No browser path to Realtime either. App users are not Supabase Auth users, so a browser could not authenticate to Realtime even if it wanted to.
  • One authorisation layer. Keeping the key server-side puts all authorisation in one place: the gate, the handler checks, and service-role-only RPCs.
  • A small, cheap relay. One upstream subscription per server stays cheap no matter how many tabs are open. The job events and the portal's chat pings carry no data, only "re-read", so a portal stream cannot leak another company's records. Each screen re-fetches through its own scoped API. Only the admin-only team stream carries thread summaries with message previews.
