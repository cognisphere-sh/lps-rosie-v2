Deployment and operations

LPS runs as two background services on one Linux server: the web app people use, and the harness that runs the AI agents. nginx sits in front of both and handles HTTPS. One private settings file drives everything, and deploying a change takes one command.

OperatorsEngineersReference~25 min read

In short

If you read only this section, these are the main points:

  • Two programs on one server. The web app (built with Next.js) is what the LPS team and supplier partners open in a browser. The harness runs the four AI agents (Rosie, Daisy, Nova and Lily) and has its own operator console. Both run as system services. They restart on their own if they crash, and they start when the server boots.
  • nginx is the front door. The internet talks only to nginx. nginx handles the HTTPS certificates (from Let's Encrypt, renewed automatically) and passes each request to the app or to the console. The harness console binds to 127.0.0.1. The app's next start gets no host name, so it listens on all interfaces. Its port is closed to the outside by the firewall that the provisioning scripts set up, which opens only HTTP, HTTPS and SSH.
  • One settings file. A private file called config holds the domain names, ports and keys. It is never committed to git. A script turns it into the private files each program reads. Passwords and keys are never printed on screen.
  • Deploying is one command: git pull && sudo ./scripts/server.sh restart. The script skips reinstalling and rebuilding when nothing relevant has changed, so a restart with no changes is quick. If a build fails, the running services are left alone.
  • Backups. When backups are switched on, the whole app folder (with its local databases copied safely) is zipped and uploaded to cloud storage on a schedule. By default the newest 14 copies are kept. Business data lives in the hosted Supabase database, which this backup does not include.
  • Accounts. An administrator creates internal staff accounts by running a small script on the server. By design, nothing in the settings file can create an admin. Supplier logins are created inside the app.
  • Quality checks. The app has 70 automated test files and a type-checker. The deployment scripts have their own tests, including one that fails if any script would print a secret. Changes to the user interface also get a screenshot review at four screen widths before they go live.
  • House rules. Anyone changing the code keeps changes small and checks them before calling them done. They never edit the installed harness library and never commit secrets. They update these docs and the changelog in the same change.
This handbook is public

Every /docs/*.html page can be read without signing in. The app's sign-in gate skips any path that ends in a file extension. That is why these pages never contain real domain names, secret values or customer data. They contain only key names, file paths and behaviour.

Runtime topology

Production is a single Linux host (Ubuntu or Debian). The repo has provisioning scripts for both an AWS EC2 instance and a Contabo VPS. Two long-running processes run on it, each as a systemd service under a non-root user. Business data, sign-in and file storage are in Supabase, a hosted service outside the server.

Componentsystemd unitWorking dirStart commandDefault port
Harness (agents and operator console)<NAME>-harness.serviceharness/$PNPM_BIN exec cognisphere serve --port $HARNESS_PORT3142, bound to 127.0.0.1
User-facing app (Next.js 16)<NAME>-app.service (only when app/package.json exists)app/$PNPM_BIN start (runs next start)3000, passed as env PORT. No host is set, so it listens on all interfaces. nginx reaches it on 127.0.0.1

NAME is ${APP_NAME:-$(basename "$ROOT")}. When APP_NAME is blank in config, the units, the nginx site and the backup cron file are named after the checkout directory. The production value is set in the private config, so this handbook writes unit names as <NAME>-harness.service and <NAME>-app.service.

Graceful shutdown

Browsers keep server-sent event (SSE) streams open for live updates (see Chat and live updates). Before 2026-09-30 those open streams made the app wait for systemd's full 90-second stop timeout on every restart. Now app/lib/server-shutdown.ts (onServerShutdown) registers one process.once handler for SIGTERM and SIGINT that closes all SSE listeners, and Next.js can then finish its normal shutdown. In an isolated test with an SSE request open, shutdown took about 6 seconds.

Host sizing

The host has about 8 GB of RAM plus 4 GB of swap (the swap was added on 2026-10-05). A Next.js build or a typecheck peaks at around 3 GB. Run only one heavy step at a time on the production box: typecheck, preview build, app build or headless browser.

nginx, domains and TLS

Two public host names point at the server through DNS A records. nginx sends each one to its own local port.

Host name (config key)Proxied toServes
$DOMAINhttp://127.0.0.1:$APP_PORT (3000)The LPS app: admin UI, supplier portal, public links, this handbook
$CONSOLE_DOMAINhttp://127.0.0.1:$HARNESS_PORT (3142)The harness operator console

Site file

  • setup-server.sh writes /etc/nginx/sites-available/<NAME> and links it into sites-enabled/. It removes the stock sites-enabled/default, then runs nginx -t && systemctl reload nginx.
  • The site file has two server { listen 80; } blocks, one per host name. Each has a shared location / proxy block with proxy_http_version 1.1, the Upgrade and Connection "upgrade" headers (for WebSockets and streaming), Host, X-Real-IP, X-Forwarded-For and X-Forwarded-Proto.
  • The harness console binds to 127.0.0.1 only. The app listens on all interfaces, so the firewall is what keeps port 3000 private. scripts/aws/setup.sh creates a security group that opens 80 and 443 (and SSH only from your IP unless SSH_OPEN=true). scripts/contabo/setup.sh enables ufw with OpenSSH, 80 and 443. With those in place, nginx is the only public way in.
  • When app/ has no package.json, only the console block is written and certbot asks only for $CONSOLE_DOMAIN.

HTTPS

certbot --nginx -d $CONSOLE_DOMAIN [-d $DOMAIN] --non-interactive --agree-tos -m "$EMAIL" --redirect gets the certificates and adds an HTTP-to-HTTPS redirect. The DNS A records must already point at the server before this step. Renewal uses certbot's own systemd timer, so no cron entry is needed.

Upload size limit (deployment hook)

At the end of provisioning, after certbot, scripts/app/setup-server.sh runs scripts/app/configure-nginx-upload-limit.py. That script adds one managed block, between the markers # BEGIN LPS APP UPLOAD LIMIT and # END LPS APP UPLOAD LIMIT:

location ~ ^/api/(?:chat/[^/]+/upload|partner/[^/]+/chat)$ {
    client_max_body_size 25m;
    proxy_pass http://127.0.0.1:<APP_PORT>;
    …
}
  • This raises the proxy limit to match webchat's 25 MiB per-file cap. It applies only to the internal chat upload route and the partner chat route (which uploads with ?upload=1). Every other path keeps nginx's built-in default body limit (1 MiB, not set anywhere in this repo).
  • The script edits only the single server block that has both server_name $DOMAIN; and proxy_pass http://127.0.0.1:$APP_PORT;. It refuses to run if it finds zero or more than one such block, an unbalanced file, duplicate markers or no location /.
  • Running it twice changes nothing; it writes atomically, keeps the file's mode and owner, and prints updated … or unchanged …. Then the hook runs nginx -t and reloads.

Request routing inside the app

After nginx, a request reaches the Next.js app. Two files decide what happens next. They are covered in detail on Architecture and Auth, roles and security. These are the parts that matter for operations:

  • Sign-in gate (app/proxy.ts). Its matcher is /((?!_next/static|_next/image|favicon.ico|.*\.[^/]+$).*), so any path that ends in a file extension skips the gate. That covers the PWA manifest, icons, sw.js and this handbook under app/public/docs/. Public prefixes are /login and /api/auth, plus the public availability, order and artifact link patterns. An unauthenticated /api/* request gets 401 {"error":"unauthorized"}. An unauthenticated page request is redirected to /login?next=….
  • One rewrite (app/next.config.ts). Only /api/gws/oauth/callback is rewritten to ${HARNESS_URL}/api/gws/oauth/callback. Google redirects the browser there, and the harness checks a single-use state value. All other calls to the harness go server to server through route handlers (app/app/api/harness/[...path]/route.ts, which has an allowlist, and app/app/api/chat/[...path]/route.ts). Those calls carry Authorization: Bearer $HARNESS_APP_SECRET and X-App-User.
  • One redirect. /portal/:path* permanently redirects to /partner/:path*, so supplier links sent before the portal was renamed (2026-08-26) still work.
  • Dev origins. allowedDevOrigins is set from DOMAIN and DEV_ORIGIN. It matters only under next dev.

npm and pnpm configuration
  • The root package.json (lps-rosie-v2, private) has no scripts. The workspace members (pnpm-workspace.yaml) are harness and app. From the repo root, run app scripts with pnpm --dir app <script>.
  • pnpm-workspace.yaml sets verifyDepsBeforeRun: false so that pnpm run and pnpm exec never install anything implicitly. It also lists allowBuilds for @google/genai, better-sqlite3 (the harness session database), esbuild, protobufjs and sharp. minimumReleaseAgeExclude lists the pinned harness versions.
  • .npmrc has verify-deps-before-run=false (for older pnpm) and @cognisphere-sh:registry=https://npm.pkg.github.com. The auth line is deliberately not in the project .npmrc, because pnpm won't expand environment credentials from a committed project file. Instead, setup-server.sh appends the literal reference //npm.pkg.github.com/:_authToken=${COGNISPHERE_NPM_TOKEN} to the run user's ~/.npmrc. The token value itself is never written there.
  • GitHub Packages needs a token with read:packages even for public packages. Without a token you get 401, and with a token that lacks the scope you get 403.
  • The harness dependency @cognisphere-sh/cognisphere-harness is pinned at 0.12.0 in harness/package.json. harness/harness.json records data version 0.12.0 and timezone America/Chicago.

Secrets handling policy

Never print a secret

Secret values must never reach the screen, logs, command lines, chat, git or these docs. That covers passwords, API keys, bearer secrets, session keys and storage keys. Refer to them by key name only. This rule applies to people and agents alike.

  • File permissions. Every generated secret file is written with mode 0600 (write600 in server.sh, chmodSync(…, 0o600) in secrets.sh).
  • Confirmations only. Scripts print messages like >> operator login configured for "<user>" (password hidden), >> wrote harness/.secrets/users.json + app/.env.local from config, >> artifacts: wired for … and >> supplier-events + webchat portal: app→agent secrets wired …. They never print the values.
  • Enforced by a test. scripts/deployment-secret-output.test.py scans every scripts/**/*.sh for echo, printf, console.log/error/warn or process.stdout/stderr.write statements that interpolate secret-looking names (PASS, SECRET, TOKEN, ACCESS_KEY, PRIVATE_KEY, CREDENTIAL…). Redirecting into a file counts as writing the file, not as output.
  • Hook rule. Deployment hooks in scripts/app/ run under set -euo pipefail, so a failing hook aborts the caller. Hooks may say that a secret was written. They must write values straight to 0600 files and never send them to stdout or stderr.
  • Rotating the console password. Edit APP_PASS in config with an editor that doesn't echo it, then run sudo ./scripts/server.sh secrets. Don't put the value on a command line.
  • Reuse across restarts. Generated secrets are reused so that sessions and links survive a restart: APP_PASS from users.json, app-secret from its file, APP_SESSION_SECRET from the existing .env.local, and the artifacts, supplier-events and webchat secrets from secrets.json. Deleting one of these rotates it. If APP_SESSION_SECRET changes, everyone is signed out of the app.
  • Git. .secrets/, config, app/.env.local and session data are gitignored and must stay that way.
  • Backups contain secrets. The backup zip includes harness/.secrets/, so the backup bucket must be private.
  • Harness model and plugin keys (such as models.json and the Gmail credentials under gws/) are managed in the harness console and stored in harness/.secrets/. They are never written into the repo.

Scripts: setup-server, server and build

The block should be removed once upstream fixes the ownership.

scripts/build.sh [all|app|harness] [--if-needed]

This script installs dependencies and builds the app. With --if-needed, it reuses earlier successful work whenever the content fingerprints still match.

  1. Lock. Takes an exclusive flock on .server-build.lock, so builds that run at the same time wait for each other.
  2. Install check. It runs pnpm install --frozen-lockfile if any of these is true: the run is not incremental; the dependency stamp (node_modules/.cache/server-build/dependencies.sha256) is missing or different; the installed harness package is missing; or app/node_modules/next is missing. Before installing it deletes both stamps, because an install invalidates the app build. It looks up COGNISPHERE_NPM_TOKEN only when an install is needed. Otherwise it prints >> dependencies unchanged — skipping install.
  3. App build check (skipped for target harness). It skips the build and prints >> app inputs unchanged — skipping build only when all of these hold: the run is incremental, no install happened, app/.next/BUILD_ID is non-empty, required-server-files.json, .next/server/ and .next/static/ exist, and app/.next/.server-build.sha256 equals <fingerprint> <BUILD_ID>. Otherwise it runs pnpm --dir app run build (next build).
  4. Stale-build guard. After building, it fingerprints the inputs again. If they changed during the build, it exits 1 with >> app inputs changed during build — rerun before restarting, so a restart never runs on a stale build.
  5. Done. It prints >> build ok — apply with: sudo ./scripts/server.sh restart. Every script uses set -euo pipefail, so a failed install or build stops server.sh before systemctl restart, and the running services are left untouched.
How the build fingerprint is computed

scripts/lib/build-fingerprint.mjs <dependencies|app> <root> prints one SHA-256 hex line. It is made of content hashes only, so it never stores source code or environment values in clear text.

  • Both modes: Node version, platform and architecture, BUILD_PNPM_VERSION, NODE_ENV. It also hashes the files package.json, pnpm-lock.yaml, pnpm-workspace.yaml, .npmrc, .pnpmfile.cjs/.mjs, harness/package.json, harness/.npmrc, harness/pnpm-lock.yaml, app/package.json, app/.npmrc, scripts/build.sh, the fingerprint script itself, node_modules/.modules.yaml and node_modules/.pnpm/lock.yaml (which catches installs done outside the script), plus the patches/ tree. Missing files hash as <missing>.
  • app mode also hashes: the trees app/ and harness/plugins/ (the app imports shared webchat types from there), excluding node_modules, .next, .build-work, .git, next-env.d.ts and *.tsbuildinfo. It also folds in the values of TZ, NODE_OPTIONS, every exported NEXT_* variable, and every name referenced as process.env.NAME or process.env['NAME'] in JS/TS source under those trees. Values feed the hash and are never stored.
  • Consequences: a regenerated .env.local with identical content triggers no rebuild, because the check uses content, not modification times. Force a rebuild with sudo ./scripts/server.sh build && sudo ./scripts/server.sh restart after changing installed packages by hand, adding build inputs outside app/ or harness/plugins/, or reading environment variables dynamically instead of through a literal process.env.X.
  • This incremental build was added on 2026-09-30. It is a local change to the harness-owned server.sh and build.sh, plus the new build-fingerprint.mjs, and it must be preserved on every harness upgrade.

scripts/setup-server.sh (one-time, re-runnable, as root)

  1. Preconditions. It needs a config file and root.
  2. Packages. apt installs curl ca-certificates nginx zip sqlite3, the agent runtime dependencies python3-venv python3-pip ffmpeg poppler-utils postgresql-client jq, the Chrome libraries for agent-browser (best effort, warns on failure), certbot python3-certbot-nginx and awscli.
  3. Node and pnpm. Installs NodeSource Node $NODE_MAJOR, then runs npm install -g corepack@latest, corepack enable and corepack prepare pnpm@latest --activate.
  4. Package registry token. Uses the config token, or falls back to gh auth login/refresh -s read:packages as RUN_USER. Adds the ~/.npmrc auth reference.
  5. Secrets. Creates harness/.secrets owned by RUN_USER and runs server.sh secrets as that user.
  6. Build. Runs a forced scripts/build.sh as RUN_USER.
  7. Agent bootstrap. Runs each harness/agents/*/bootstrap/bootstrap.sh as RUN_USER (best effort). These build each agent's .venv (markitdown, ddgs) and install pi and agent-browser.
  8. systemd units, as described under Runtime topology.
  9. nginx site, then certbot, as described under nginx, domains and TLS.
  10. Backup cron, as described under Backups.
  11. Deployment hook scripts/app/setup-server.sh sets the upload limit. The script finishes by printing the app and console URLs.

Backups

When BACKUP_S3_BUCKET is set, a cron job uploads a zip of the whole app folder to S3 or S3-compatible storage on a schedule and prunes old copies.

What the backup does not cover

The zip holds files on the server: the harness SQLite session database, agent files, secrets and the git checkout. Business data (suppliers, plants, jobs, availability requests, orders, accounts and chat transcripts) lives in Supabase, and its protection is Supabase's own backups. The zip also contains secrets, so keep the bucket private.

Creating admin accounts

Internal staff accounts (role admin) can only be created from the server's command line. No key in config creates an admin. That replaced an older ADMIN_USER/ADMIN_PASS seed on 2026-08-30. Supplier (partner) logins are created in the app, from the Portal access panel on the supplier page (see Supplier portal and public links).

cd app && set -a && source ../config && set +a && node scripts/create-admin.mjs <username> '<password>'
  1. Requirements. SUPABASE_URL and SUPABASE_SECRET_KEY must be set (the script exits 2 otherwise). It also reads AUTH_EMAIL_DOMAIN.
  2. Derive the sign-in email. The handle is username.trim().toLowerCase(). If the handle contains @, it is the email. Otherwise the email is <slug>@<AUTH_EMAIL_DOMAIN>, where runs of characters outside [a-z0-9._-] become - and leading or trailing dashes are dropped. This is the same derivation lib/auth.ts uses, and the two must not drift apart.
  3. Look up app_users by the normalized handle:
    • Existing non-admin (for example, a partner): the script refuses and exits 1. Reset that account from the supplier page instead.
    • Existing admin: updates the password (action: "password-reset").
    • New: creates a confirmed Supabase Auth user (no email is sent to the .invalid address), then inserts app_users {id, username, role: 'admin', supplier_id: null}. If the insert fails, the auth user is deleted again, so no stray identity is left behind (action: "created").
  4. Verify. Signs in with the new password on a separate throwaway client. Signing in on the service client would make its later calls run as an ordinary signed-in user instead of the service role.
  5. Report. Prints JSON with username, authEmail, role, userId, action and signInVerified. It never prints the password. If verification fails, it warns and exits 1.
Pitfalls

The password is passed as a command-line argument, so it lands in shell history. Prefix the command with a space (if your shell ignores such lines) or rotate the password afterwards. Keep AUTH_EMAIL_DOMAIN set in config. If it is missing, create-admin.mjs and lib/auth.ts fall back to app.invalid, but scripts/app/secrets.sh writes lps-app.invalid into .env.local, and the derived emails would no longer match.

Release verification

Routine code changes

This is the current procedure for shipping a change, as used by Nova (the developer agent) and anyone else working on the box. It was simplified on 2026-10-05.

  1. One builder thread per request, and builder threads do not start threads of their own. Trivial fixes may be done directly.
  2. Edit on main in the primary checkout, and stage only your own paths.
  3. Check. Run pnpm --dir app typecheck and the relevant test files (pnpm --dir app exec tsx --test <file>). Don't run the full suite on the host.
  4. UI review (UI changes only). Use the visual-ui-release-qa skill (v2.0.0). scripts/preview start --commit <sha> --port 3100 builds that commit in a temporary worktree served on 127.0.0.1:3100, so the live app is never touched. Sign in with scripts/login, which reads its credentials from the VISUAL_QA_USERNAME and VISUAL_QA_PASSWORD environment variables without echoing them. Capture every affected state at widths 320, 390, 480 and 1440. A fresh reviewer thread records PASS or FAIL in review.md. A FAIL blocks the deploy, a preview that won't build counts as a FAIL, and a second FAIL goes to a human.
  5. Deploy. Commit, then run sudo ./scripts/server.sh restart app. It builds as part of the restart, so no separate build step is needed.
  6. Report once. Say what changed, give the commit, confirm it is live, and include a screenshot for UI work. Rollback is git revert <sha> and the same restart.
Rules around the loop

A human saying "deploy" is the authorization, and only humans may add extra gates. Because of the host's memory, run only one heavy step at a time: never two of typecheck, preview build, app build and browser at once. Stop the preview and close the browser before restart app.

Harness-side changes

Per CLAUDE.md §5, run the app's checks. A harness-side change also needs a server restart that comes up clean: every agent running and no plugin failed. A task is not complete while any check reports errors. Nova leaves harness restarts to a human operator (sudo ./scripts/server.sh restart harness), which regenerates secrets and does not compile the app.

Harness upgrades

The harness is an installed, versioned package (@cognisphere-sh/cognisphere-harness, currently 0.12.0), not a fork. Version bumps go through the cognisphere-upgrade skill (v1.3.0, in .claude/skills/). In this deployment, Nova also has that skill. An upgrade has two phases: code (bump the dependency) and data (edit the harness data folder to match, then stamp harness.json).

  1. Check the window. cognisphere upgrade prints the data version, the code version, and the changelog's breaking changes between them. If it says up to date, stop. If the data is ahead of the code, bump the code first with cognisphere upgrade --to <target> or pnpm add @cognisphere-sh/cognisphere-harness@<target>.
  2. Read the breaking changes, oldest first. Each entry looks like - <what changed> [affects: <path glob>].
  3. Plan surgical edits. These cover agent.json field moves, 0-* base prompts replaced by the new seed (local edits move into 1-agent.md), seeded prompts and scripts grafted onto local forks, and plugin contract changes. Secret reshapes are described for the operator, and .secrets/ values are never edited or printed. Procedural content found in prompts moves into versioned skills.
  4. Refresh the harness-owned scaffold: scripts/, config.example, docs/base-harness/, .claude/skills/, app/artifacts-routes/, and app/auth-routes/ when it exists (this home has none).
    • Diff each one against the package's home-template and skills, using git log to tell upstream changes from local edits.
    • Copy in the shipped versions, including the changelog into docs/base-harness/CHANGELOG.md.
    • Check user-owned copies of the artifacts template for drift. They are never overwritten, and security-relevant upstream changes are called out.
    • Re-apply local edits. A local edit is dropped only with explicit operator approval.
    Never refreshed: app/ (apart from the two template folders), docs/harness/, docs/app/, CLAUDE.md, config, the harness data folder, and everything in scripts/app/ except its README.md.
  5. Review. git add -A && git diff --staged, then wait for explicit approval.
  6. Stamp and restart. cognisphere upgrade --set-version <code-version>. The operator reviews, commits and runs sudo ./scripts/server.sh restart, then checks for a clean start.
Local edits to preserve on every upgrade
  • Incremental build. scripts/server.sh, scripts/build.sh and scripts/lib/build-fingerprint.mjs carry the 2026-09-30 incremental build. These scripts are harness-owned, so re-apply it after refreshing them.
  • Ownership workaround. scripts/app/secrets.sh holds the app-secret ownership workaround. Remove it once upstream fixes the bug.
  • Version pins. The pins live in harness/package.json and in pnpm-workspace.yaml under minimumReleaseAgeExclude. Update both.
