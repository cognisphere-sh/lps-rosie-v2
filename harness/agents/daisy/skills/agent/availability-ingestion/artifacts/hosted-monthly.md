# Monthly checks of designated hosted lists

Chris, 2026-10-16, Telegram1410: “monthly, not weekly. We should designate the ones that host so we dont do extra work”. This is a selective monthly review, not all Hosted suppliers or a crawler.

## Scope and timing

The explicit selection register is `workspace/hosted-monthly/designations.json`. Each entry names supplier id, owning thread, exact landing/list URL, designation evidence, URL-verification evidence, status and schedule. Never enroll from `availability_source_type = Hosted` alone. Add suppliers only from Chris/Bhoumik's explicit designation; unresolved selection or URL stays pending, unscheduled. Removing/pausing review is not deactivating inventory or sources.

Use existing scheduler, targeting the owning supplier thread. Record America/Chicago day/time and bounded load before activation; confirm the scheduler's effective timezone. Monthly review cadence is not `suppliers.availability_update_days` (supplier publishing frequency); leave that field alone. Leave paused onboarding/backfill untouched. Default first-run proposal is the next monthly anniversary at 09:30 America/Chicago; stagger any later selected suppliers rather than launch a blanket batch.

## Each fire: on the supplier thread

1. Read the register entry and `ingest-context`. Check thread notes and active ingestion tasks first. Serialize all email, manual and hosted processing for this supplier: if an ingest is running, queue this check on its existing thread; do not start another worker or write concurrently. One parsing task per receipt remains the limit. No supplier/customer contact.
2. Fetch the designated page using the existing web wrappers and inspect the actual availability material, following linked lists/PDFs/workbooks even when landing HTML or displayed dates are unchanged. Download linked availability files to `/tmp`; read relevant page/list text, dates and amendments. Do not crawl unrelated website pages. Missing links, login/access errors or unreadable material are failures/blocked checks, never unchanged or zero stock.
3. Compare the whole effective material against the last **fully successful, QA-verified** receipt for the same supplier/location. Include all relevant linked files and material body amendments (including email changes to prices, scope or farms). Use `source-check` with stable filenames, scope and context per [source](source.md). Keep retrieval time, channel and incidental HTML separately in check provenance, not in the stable effective-content comparison. Preserve printed dates, actual availability text and meaningful amendments. Never drop an amendment to force a fingerprint match.
4. `source-check` is byte/name/rules-sensitive, not a universal cross-channel content matcher. Review recent email/manual source evidence too: a website file may already have been ingested by email under a different scope/name. Verify original files and amendments, locations, receipt/effective-date basis, source ids and successful QA. An unamended web copy does not erase an email amendment. Skip only when all effective content is already successfully handled (or is an older unamended base of the already-handled amended list), citing the prior source ids and comparison basis. If bytes differ only in incidental formatting/HTML, establish equivalence from the actual source contents; if uncertain, do not call unchanged. Rule changes still require reprocessing as the existing helper specifies.
5. New or materially changed content follows normal source, location, manual-current-receipt, page-by-page ingestion and QA rules. A monthly fetch is a new manual observation, not a supplier publication date or fresh stock confirmation. Static public lists remain confirmation-needed placeholders. Future-dated material: preserve it, schedule one-shot handling on the effective date on this supplier thread, and record deferred status, not a successful ingestion receipt. Do not renew a future schedule for the same preserved material on each check.
6. Failed/partial attempts never advance the successful comparison baseline or record a success receipt. Reuse staged work/source evidence safely on retry; recheck current sources before writes. Only verified completed ingestion can call `source-check record`. An unchanged cross-channel comparison is documented with existing source evidence, not falsely recorded as newly ingested.
7. Finish via [finish](finish.md): supplier-panel result and daily-note summary, no routine Telegram/progress messages. Include checked URL/date, unchanged with prior source ids, changed ingest counts, deferred date, or failure/partial/blocker and next action. Keep the latest check evidence and prior successful source references in `workspace/threads/<supplier-thread>/files/hosted-monthly-check.json`; do not overwrite successful references with failed checks. This file is operational evidence, not a new DB receipt contract. Store durable source material through existing storage rules, not scratch workspace copies. Report real decision blockers through the existing panel/main routes; never silently retire inventory/sources or reinterpret a failed fetch as no plants.

## Limits

Schedule activation is not a completed check. Initial supplier URL/import verification is not a monthly run. Existing helpers require source inspection and supplier-thread coordination; this procedure promises neither unattended all-format crawling nor automatic semantic email/web deduplication. Unsupported content stays an explicit failure/parked part while supported work finishes.
